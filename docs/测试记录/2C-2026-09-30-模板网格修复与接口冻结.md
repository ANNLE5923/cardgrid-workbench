## 2. 根因

- 模板条目 `start` 字段在 [workspace-format.ts](../../src/workspace-format.ts) 的 `templateShape` 中使用 `clockValue`，该校验只匹配正则 `^(?:[01]\d|2[0-3]):[0-5]\d$`（HH:mm 格式），**不校验分钟是否落在 5 分钟网格**。
- `validateActionData` 的模板条目循环只检查了 `entry.elapsedMinutes % 5`（时长须为五分钟倍数），**缺少对 `entry.start` 的网格检查**。
- 对照：计划与固定块的网格在 `assertActionState` 中经 `assertPlannedRange → plannedRange`（[action-time.ts](../../src/action-time.ts)：`if (local.minute % 5) throw INVALID_GRID '起点须落在 5 分钟网格'`）拒绝；而 `assertActionState` 中**没有模板条目循环**，模板此前只查了唯一 ID 与版本，故漏检。

### F01 根因（相邻日未准备模板的跨午夜占用）

- 投影层已有 [projectedTemplates](../../src/action-projection.ts)：对**没有 Day 记录（未准备）**的日期，按其星期匹配模板并生成虚拟模板占用；`compatibilityFor(data, range)` 在传入 range 时会从 range 起始的前一天到结束日逐日期投影。
- 但准备日的两个冲突检查调用点（PrepareDay、previewDayTemplate）都调用 `calendarConflicts(data, operation, compatible(data))`，**第三个参数 `compatible(data)` 不带 range**。`compatibilityFor` 在 range 为空时直接返回 legacy 占用、不投影任何模板，于是相邻日的跨午夜模板段不进入冲突检测。
- **前日方向**：周日模板 `sun` 有条目 23:30、120 分钟（23:30—01:30 跨午夜）；周日未准备，没有固定块。准备周一时，周一模板 00:00、30 分钟（00:00—00:30）与周日溢出段重叠，检查却返回零冲突。
- **次日方向（首轮修复遗漏）**：周一模板 `mon` 条目 23:30、120 分钟（23:30—次日 01:30）；周二未准备，其模板有条目 00:00、30 分钟（00:00—00:30）。准备周一时，周一固定块溢出到周二的部分与周二模板重叠，但首轮修复只投影前一天、未投影次日，仍零冲突保存。
- 对照：若相邻日**已准备**，跨午夜条目已生成真实固定块，常规占用检测能发现；缺陷只发生在相邻日未准备、固定块不存在时。
- 关键教训：既有 F01 测试只覆盖前日方向，15/15 全绿不能证明跨日检测完整；必须按新增固定块的**完整区间**覆盖两个方向。

## 3. 2C 修复

### F02 修复

只修改授权文件 `src/workspace-format.ts`，在 `validateActionData` 的模板条目循环中、与时长网格检查并列，新增起点网格检查：

```ts
p.templates.forEach((template, i) => {
  uniqueIds(template.entries, `${path}.planner.templates[${i}].entries`);
  template.entries.forEach((entry, j) => {
    const startMinuteOfDay = Number(entry.start.slice(0, 2)) * 60 + Number(entry.start.slice(3));
    if (startMinuteOfDay % 5) fail(`${path}.planner.templates[${i}].entries[${j}].start`, '起点须落在 5 分钟网格');
    if (entry.elapsedMinutes % 5) fail(`${path}.planner.templates[${i}].entries[${j}].elapsedMinutes`, '时长须为五分钟倍数');
    if (entry.definitionId) refCheck({ kind: 'definition', id: entry.definitionId }, `${path}.planner.templates[${i}].entries[${j}].definitionId`);
  });
});
```

为什么放在这里：

- `validateDefinitionConfig` 内部构造 Data 后调用 `validateActionData`，因此这一处检查**同时覆盖 backup 与 config 两条路径**，与 2B-F02 两个失败变体一一对应。
- 与既有 `elapsedMinutes % 5` 网格检查放在同一循环，保持两类网格约束集中、口径一致；错误信息与 `plannedRange` 完全对齐（“起点须落在 5 分钟网格”）。

### F01 修复

修改 `src/action-commands.ts`：从 `action-time` 增导入 `nextDate`、`dateAt`，从 `action-projection` 导入 `projectedTemplates`，从 `action-domain` 增导入 `Occupancy` 类型；在 `calendarConflicts` 内**按新增固定块的完整区间**收集相邻日期的未准备模板占用：

```ts
function calendarConflicts(data: DataV2, operation: Extract<ActionOperation, { type: 'ApplyCalendar' }>, compatibility?: CompatibilityOccupancy): readonly Overlap[] {
  const changedIds = new Set(operation.fixed.map(f => f.id));
  const filtered = { ...data, planner: { ...data.planner, fixed: data.planner.fixed.filter(f => !changedIds.has(f.id)) } };
  const changed = operation.fixed.filter(f => !f.cancelled);
  const zone = operation.day.zone, ownerDate = operation.day.date;
  // Project unprepared day templates for every calendar date reached by the new fixed blocks' full ranges.
  // The window opens one day early (a previous day template can spill into the owner day) and excludes the
  // owner date, whose own template is being instantiated; otherwise it would conflict with itself.
  let firstDate = nextDate(ownerDate, -1), lastDate = ownerDate;
  for (const item of changed) {
    const startDate = dateAt(item.range.startAt, zone), endDate = dateAt(item.range.endAt, zone);
    if (startDate < firstDate) firstDate = startDate;
    if (endDate > lastDate) lastDate = endDate;
  }
  const projected: Occupancy[] = [];
  for (let date = firstDate; date <= lastDate; date = nextDate(date))
    if (date !== ownerDate) projected.push(...projectedTemplates(data, date, zone));
  const withSpill: CompatibilityOccupancy | undefined = projected.length
    ? { unknown: compatibility?.unknown ?? false, items: [...(compatibility?.items ?? []), ...projected] }
    : compatibility;
  const result: Overlap[] = [];
  for (const [i, item] of changed.entries()) {
    result.push(...overlaps(filtered, item.range, undefined, withSpill).map(c => ({ ...c, id: `${item.id}->${c.id}` })));
    for (const other of changed.slice(i + 1)) { const overlap = intersectRanges(item.range, other.range); if (overlap) result.push({ kind: 'fixed', id: `${item.id}->${other.id}`, title: other.title, range: other.range, overlap }); }
  }
  return result;
}
```

为什么这样修：

- `calendarConflicts` 是 PrepareDay 与 previewDayTemplate 共用的唯一冲突函数，在此补齐则两条路径、两个方向同时生效：预览分别返回含 `sun`（前日）或 `tue`（次日）的冲突，PrepareDay 因冲突非零而返回 `OVERLAP_CONFIRMATION_REQUIRED`。
- 日期窗口直接由新增固定块的起止时刻（`dateAt` 到各自时区）推出，并提前一天开窗，与 `compatibilityFor` 的相邻日窗口口径一致；不是再硬编码加一天。
- 复用 `projectedTemplates` 保证与读盘（projectDay）对未准备模板的可视化口径、ID 和歧义处理一致；它在相邻日已有 Day 记录时返回空数组，故已准备日仍由真实固定块检测、不会重复计数。
- 不跨午夜的相邻条目与新增固定块不相交，`intersectRanges`（要求严格 start<end）返回 null，不误报；结束恰好落在午夜也不算重叠。

- 未改独立测试、未删除任何断言、未扩写其他时间语义（如条目溢出当日等不在本次范围）。
- 校验不修改输入：2B-F02 测试中的 `assert.deepEqual(value, before)` 通过。

- 相邻日有多个匹配模板时，`projectedTemplates` 抛 `AMBIGUOUS_DAY_TEMPLATE`，与读盘口径一致，不擅自选第一个。
