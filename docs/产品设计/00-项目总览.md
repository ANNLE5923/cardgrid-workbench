# 项目总览

> CardGrid 的设计入口。先读本文，再读[功能地图](01-功能地图.md)、[系统架构](02-系统架构.md)、[项目决策与问题](03-项目决策与问题.md)和[后续路线图](04-后续路线图.md)。本文同时区分**现有 P1A 事实**与**2026-09-24 AI Talk 讨论形成的产品方向**；讨论稿不是已实现规格，也不自动决定 P1B 范围。

## 1. 项目是什么

- **产品方向的一句话定义**：CardGrid 希望通过可重抽、可手选的卡牌建议降低“现在做什么”的决策成本；以 Today 的一天时间图组织计划和行动，再把用户确认过的实际发生之事沉淀为生活记录。
- **当前产品形态（2026-10-02）**：正式行动定义、抽卡/手选、手牌、排期与实际事实/批注已接入；“抽卡手牌 → 当日”使用权威双环与拖动手牌，主要页面已统一。G2/G3经分离验收放行；工作树仍未提交/发布，实体触屏和连续真实使用未验收。见[G3验收记录](../测试记录/G3-2026-10-02-有界修复与最终验收.md)。
- **目标用户**：希望自主安排时间和任务、又常在“选择太多而难以开始”时需要轻推一把的个人用户，包括学生、创作者、独立开发者和知识工作者。
- **不是**：用随机结果命令用户、把未完成当作失败，或要求现实服从预定日程的严格自律系统。

## 2. 为什么做

用户可能已经知道很多可做的事，却在“做什么都行”时缺少发起行动的推力。传统日历、待办和笔记还将计划、临时决定与生活事实分开保存。CardGrid 试图形成一条顺畅链路：

```text
不知道现在做什么 → 抽取建议或手动选择 → 暂存手牌
→ 安排进今天可用时间 → 现实变化时自由调整
→ 用户确认实际发生 → 自然形成可回顾的生活记录
```

**随机是建议，不是命令。** 用户可以接受、重抽或完全跳过抽卡。计划是可修改的暂时安排；时间流逝本身不证明行动已发生。完成后原事实永久不可修改已由用户定案；数据表示、录错说明与旧数据迁移边界已在正式合同中冻结并实现；真实迁移需用户授权执行。

## 3. 产品原则

1. **降低开始行动的决策成本**：抽卡提供候选答案，不替用户做主；手动选择始终存在。
2. **Today 是行动场，不只是任务列表**：长期方向是一张完整的一天时间图，让固定安排、可用时间、临时行动和记录在同一视角中有明确位置。
3. **尊重现实变化**：固定安排默认受保护；尚未确认发生的计划应能改时间、撤回或重新安排，错过原定时间不自动等于失败。
4. **事实由用户确认，确认后原记录锁定**：钟表走过某个时间不自动标记完成；用户确认完成后，原事实内容和实际时间永久不可修改，只能追加带时间戳的批注。行动Host已落实事实锁定；录错通过追加批注说明，备份恢复遵循冻结合同。
5. **记录尽量从行动中自然产生**：减少晚上重新录入“今天做了什么”的成本；不同生活领域可以携带自己的结构化信息。
6. **一套候选选择能力，多种生活模块复用**：行动、锻炼、饮食、消费等可以使用共同的抽取逻辑，但不要求首版全部实现。
7. **本地优先、用户自主配置**：不预置私人生活，不以账号为前提；预设模块与卡组可以提供起点，但用户能自行创建、修改和手选。
8. **诚实描述能力**：产品愿景、领域层支持、页面可操作、已验收是四种不同状态。

## 4. 核心使用场景

### 已实现的行动循环与后续记录方向

- **不知道现在做什么**：用户从某一候选集合抽一张卡；接受、重抽或手动选择。
- **安排这件事**：卡先进入可保留和排序的手牌；打出时寻找不与固定安排冲突的自由时段，再由用户调整。
- **今天变了**：计划在确认完成前可以移动或回到手牌；临时来访、晚起、改期等都按现实记录，不给消极失败标签。
- **确认发生**：由用户明确确认实际行为和时间；后续生活记录可聚合阅读、消费等结构化数据，并允许对过去追加新的理解。

### 当前版本实际可走的场景

- 在行动定义创建一条定义，手选或抽取后保留在手牌。
- 在“抽卡手牌 → 当日”查看双环、排期、改期或撤回，确认分钟精度实际事实并追加批注。
- 快速捕获到Inbox；模板在配置JSON维护，在Schedule显式准备日型。
- 从“数据与备份”导出完整备份、预览导入和恢复。

## 5. 当前阶段

- **仓库版本**：`package.json` 为 `0.2.0`；本地实现已通过G3，仍未提交或发布。实体设备和连续真实使用证据另列。
- **已实现并验收**：正式行动闭环、双环与手牌、统一页面和响应式；数据写入走正式Host，IndexedDB事务与备份/恢复边界保持阶段2实现。详见[功能地图](01-功能地图.md)。
- **下一步**：按[后续路线图](04-后续路线图.md)先积累真实使用反馈，再设计阶段4记录回顾与第二领域；范围需用户决定，不自动开始新开发或真实迁移。
- **暂不宣称已有**：通用抽卡、手牌、24 小时双环表盘、完成事实层、批注、饮食/消费统计、AI 自动排程、云同步与多人协作。

## 6. 项目边界

**要做**：帮助个人在不确定时开始行动、在一天中灵活安排、如实记录发生的事；尽量让用户通过正常操作形成长期反馈。

**当前不做**：用规则惩罚未完成、把随机变成强制、自动判定事实、要求用户一次完成复杂配置。企业团队协作不属于当前主线。

## 7. 给后续 AI 的阅读规则

任何关于抽卡、表盘、事实锁定的讨论，先区分“方向已提出”和“规则已定案”：完成后原事实永久不可修改已定案，其它交互细节仍可能调整。先核对代码，再提出增量方案；不要把旧 `Config.Card`、Planner `Task`、未来手牌和完成事实混为一个对象。尤其不要把 UI 内的“不可编辑”称为技术上“不可篡改”：在本地浏览器中，用户仍可改写存储或恢复旧备份。设计讨论要以[项目决策与问题](03-项目决策与问题.md)中最新结论为准。
