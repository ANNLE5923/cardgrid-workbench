调整重点：

1. **收敛交互探索，转向正式闭环**：用户已确认的表盘、手牌和重叠规则作为输入；只有新的阻断证据才重新讨论。
2. **把2A拆成五个可验证断点**：格式只读、纯时间/领域、原子命令、迁移与恢复、正式Host和入口切换。逐步交证据，2B仍保留独立回归职责。
3. **避免两次建设页面**：阶段2的排期表单、完成确认、事实详情与批注是正式可复用组件；阶段3主要替换时间展示与手势入口，继续使用同一命令和详情组件。
4. **防止新旧写入口并存**：新格式启用时，旧Today/Schedule/配置等所有保存入口必须适配或明确只读；不能让旧写入绕过事实锁定。真实数据不自动迁移。
5. **修正过期范围**：允许确认后重叠；内圈00—12、外圈12—24；当前半日一个绝对落点；最小批注属于阶段2。

## 目标与排序依据

CardGrid 的下一条主线是：**不知道做什么 → 抽取建议或手选 → 保留在手牌 → 安排进一天 → 根据现实调整 → 用户确认实际发生 → 形成记录**。它服务“帮助开始行动”，不是增加一个孤立的抽卡小游戏。

阶段顺序由以下依赖决定：

1. 先区分**卡牌定义、候选/手牌实例、可改的计划、确认后的事实**。完成后原事实永久不可修改已定案（D008）；现有 `done → planned` 与之冲突，不能直接在旧状态上叠新 UI。
2. 先让**一个行动领域**跑通完整循环，再从真实差异提炼通用抽取能力；饮食、消费等不能因“复用引擎”而被迫共用不合适的字段。
3. 双环与手牌的主要交互已做原型验证。正式替换Today须等待生产时间、占用、计划/事实及存储接口稳定，保留已确认的交互成果，不重新开始整轮视觉探索。
4. 界面风格按 DESIGN.md 的 Fluent Design 原则渐进落实：阶段 1 验证任务层级与交互原型，阶段 2 的新页面沿用已确定规则，阶段 3 再统一现有主要页面。视觉调整不能改变已冻结的数据和事实语义。

继续保留可用的 P1A 数据与入口；新路线不是从零重写。阶段名称是工作划分，正式版本号在发布时再确定。

## 阶段 0｜保住当前可用版

**目的**：在下一次数据模型变化前，让用户仍能安全使用 P1A，并为迁移建立可信基线。

**工作**：核对完整备份→清空测试工作区→恢复、跨窗口冲突、历史数据导入与失败时保留输入；清理“日程操作尚未开放”等过期文案。针对“配置工坊定义与 Planner 一次性导入”“Inbox 转无日期 Card 后缺少排期入口”，先明确限制及临时使用路径，避免在旧模型上大规模堆功能。任何真实数据迁移前先让用户导出可独立保存的完整备份。

**完成门槛**：当前数据能导出和恢复；代码、功能地图与已知限制一致。若要改现有数据结构，先通过阶段 1 的迁移方案审查。

## 阶段 1｜模型与交互关口

**状态：已完成，以下是成果范围；正式语义以1F-contract-1为准。** 后续只补实现暴露的具体缺口，不将已确认的用户取舍重新变成待决问题。

**目的**：把“新愿景与 P1A 对照”变成可实施合同，而不是先改页面。

**必须产出**：

- **身份与状态图**：定义卡牌定义、一次抽取、手牌、计划块、完成事实、追加批注之间的身份与引用；说明 Inbox Capture、旧 `Config.Card`、Planner Task/Block/History 各自怎样继承或迁移。
- **状态规则**：抽取可重抽、始终可手选；手牌与计划在确认前双向可逆；钟表走过计划时间不自动完成；固定安排默认防误拖，明确解锁才可调整；用户确认完成后原事实内容与实际时间在应用内永久不可修改，只能追加批注。
- **时间与录错合同**：区分计划时间、实际起止时间、确认时间；设计跨午夜、过去日期调整、录错后追加说明、旧 `done`/`CardReopened` 数据、导入旧备份的行为。不得把本地 IndexedDB 宣称为密码学意义的不可篡改存储。
- **表盘交互原型**：用空白日、固定块密集日、跨午夜日、发生临时事件的日子验证前后 12 小时双环、当前指针、旋转、编辑与可访问的替代操作。原型是测试材料，不是提前确认最终视觉。
- **界面风格合同**：以DESIGN.md为输入，冻结导航、就近命令、4px间距、独立表面和焦点等规则；原型覆盖悬浮手牌、5分钟磁吸、径向切换内外圈、当前半日单一绝对落点、日终红色及边缘阻尼。窄屏样式检查不等于320px/390px/720px完整操作、真实触屏、读屏或高对比验收；这些证据仍需阶段2/3补齐。
- **迁移与发布方案**：保留旧数据、提供独立备份和回退路径；确定如何避免 `Config`/Planner 双事实来源。修改 schema 前写明不能静默丢失的字段及验证方式。

**完成门槛**：主路径状态表、领域不变量、迁移样例、原型测试结论、界面风格验收要点和有取舍理由的技术方案已可审阅。未解决 D008 的落地方式前，不进入阶段 2 开发。

## 阶段 2｜一张行动卡的完整循环

**范围**：只做“行动”领域；所有新卡牌定义由行动模块统一管理，简单表单与高级JSON共用数据和校验，旧配置通过显式导入与差异预览接入。一个实例最多一个活动计划和一个完成事实，重复行动建立新实例；固定日程只作安排。默认工作区空白，不自动种入演示或私人数据。

**用户路径**：抽取一张建议 → 接受或重抽；也可手选 → 放入手牌并排序 → 按预设完整时长安排，任何类型的重叠均须明确提示后确认 → 改时间或撤回手牌 → 填写实际起止（默认计划时间，允许未来结束）并确认 → 查看锁定事实、原计划对照，必要时追加说明。已完成后以实际区间占时，计划只作对照。

**实施顺序**：2A按五个断点交付内核与生命周期 → 2B独立回归 → 2C修复并冻结页面接口 → 2D/2E定义、手牌与入口集成 → 2F排期、实际确认、事实和批注 → 2G/2H正式浏览器验收与修复。每个2A断点都有当步测试，不等到2B才首次验证核心。具体文件与退出标准见线性任务计划。

**实现边界**：以正式、可访问的列表/表单承载闭环，不要求最终双环动效。确认、详情、批注与失败反馈组件继续供阶段3使用。生产组件不导入docs或原型实现；旧界面可以保留只读兼容展示，但所有写入必须经过新命令。新路径在隔离合成数据中验证后才切换启动入口；旧数据载入不自动迁移或执行每日初始化。抽卡只给候选，不自动排程或完成。

**完成门槛**：至少验证“抽/手选、重抽、打出、固定块冲突、改期、撤回、跨过原定时间仍未完成、手动确认、确认后拒绝修改、追加说明、备份恢复”整条链；真实浏览器走查通过后，用户可连续使用并反馈操作成本。只有领域测试通过而 UI 走不通，不算完成。

## 阶段 3｜Today 时间盘与界面统一

**范围**：在阶段2稳定的命令和投影上，正式接入已确认交互：内圈00—12、外圈12—24同时显示；底部指针固定，12个数字随表盘/滑块整体转动；初次指向现在，顺时针更早到00:00，逆时针更晚到24:00，两圈有界不绕回。拖滑块只改滑块，拖盘则整体转动；重叠叠色，指针命中的全部项目共同强调并列出详情。

悬浮独立手牌不受底部容器裁剪，选中转正放大查看；拖动接近盘面先外圈、进一步靠近转内圈预览，5分钟磁吸并显示完整计划信息。松手有预览则形变留盘进入保存流程，重叠先确认；无预览则回手牌。符合资格的卡牌计划可外拉回收，固定块和事实不可回收。24格竖条只读展示日程，点击查看概述，左侧现在指针可复位、右侧跟随盘面读数。日终红色按占用重算、不生成事实；滚动边缘有阻尼且不争夺拖牌手势。

**复用方式**：沿用原型的已确认行为、场景和适合提取的几何/视觉组件；重新接入正式Host并补真实保存、失败、取消、并发与刷新测试。禁止整体搬入原型App、内存Host、fixture或用删除计划模拟正式撤回。3A只核对生产投影与交互接口差异；3B/3C完成接入，3D/3E统一页面与设备适配，3F/3G独立验收放行。

**保护条件**：固定块不能因打牌被挤走；显式解锁不等于静默覆盖。过去时间不能被涂成失败；未确认计划即使原定时间已过，仍依规则可调整。确认事实不可被拖动。为视觉操作提供同等能力的列表/键盘路径。

**完成门槛**：在空白日、拥挤日、跨午夜日和 720px、390px、320px 小屏幕上能读懂和编辑；主要页面显示清楚当前视角、下一步命令与操作结果；键盘焦点、语义色、减少动态效果和滚动边缘反馈经实际检查。操作不会误改固定块或事实；可用时段计算与时间盘显示一致。若双环在关键场景无法清晰表达，应保留产品目标并调整视觉形式，而不是强推效果。

## 阶段 4｜记录可回顾，再验证跨领域复用

**先扩展记录**：在阶段2已有的事实详情、计划/实际对照和最小追加批注之上，增加跨日浏览、检索与每日回顾。批注只追加、不覆盖，不使用“失败日”等惩罚标签；不能将锁定后解释录错的基本能力延迟到本阶段。

**再选第二领域**：从餐饮或消费中选一个，用真实字段检验“候选集合 → 手牌 → 安排/发生 → 记录 → 聚合”能否复用。饮食热量、消费金额等聚合必须明确数据来源、单位与更正说明，不把演示数字当作真实统计。

**完成门槛**：同一套基础选择能力支持第二领域而不破坏第一领域；记录、批注和聚合在备份恢复后仍可核对。若第二领域需求证明通用模型过度抽象，应允许按领域扩展，不硬塞进单一 Task。

## 暂缓与明确不做

- **暂缓**：AI 自动排程、云同步、多人协作、完整项目管理、积分/惩罚机制、一次性铺开锻炼/饮食/消费/娱乐/奖励全部模块。
- **不做的产品行为**：抽中即强制执行；时间到了自动宣告完成或失败；未完成计划不可调整；把已确认事实通过正常操作撤回或覆盖。
- **不是“完成”证据**：只通过类型检查或领域测试、只有静态表盘样图、只做通用抽卡配置却没有用户闭环、只把 `Task.status` 改成 done 而无实际事实记录。
