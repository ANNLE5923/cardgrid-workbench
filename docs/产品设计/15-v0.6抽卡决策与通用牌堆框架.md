## 1. 产品目标

建立通用的“收纳 → 拿牌或抽取 → 决策 → 可选合成 → 手牌 → Today 使用”框架。吃饭、阅读、锻炼是同级用例，三者都须走通；不能以阅读卡包、单一书目槽位或三套分别硬编码的流程代替框架。

用户的成功标准是“只要行动就是成功”。随机降低选择成本，保留直接取牌、手选和重抽；合成是组合与呈现形式，不增加奖励、能力或执行义务。配置内容由用户维护，起步允许外部 AI 生成导入包批量配置；生产工作区保持空白。

记录侧形成“表盘变化 → 日记自动段；个人感想 → 独立时间戳随记；应用操作 → 维护日志”。日记与日志实际生成纯文本文件，采用 Markdown 内容组织。它们分别服务用户的生活记录和维护者的操作追踪。

## 3. 产品角色与生命周期

| 角色 | 负责什么 | 使用后如何处理 |
| --- | --- | --- |
| 行动原卡 | “读书”“吃饭”“锻炼”等可重复使用的定义，带预留字段 | 长期保留；修改不改旧手牌和事实快照 |
| 决策原卡 | “读哪本”“这餐吃什么”“练什么项目”等问题及候选来源 | 长期保留；矩阵抽取形成本次答案 |
| 收纳条目 | 书、食物、锻炼项目、想买的零食、有用网址、项目清单条目等内容 | 可整理牌堆成员关系；不强制进入行动链 |
| 牌堆 | 收纳及候选组织，可独立存在、可被多个决策引用 | 不因拿牌或合成而删掉原成员 |
| 本次行动素材 | 从工坊拿出或抽取接受后得到的独立手牌 | 合成成功后退出可用手牌，保留可核对来源 |
| 本次答案牌 | 固定的本次问题、答案和来源快照 | 可参考、独立摆放或参与合成；浏览不重新随机 |
| 合成手牌 | 本次行动与已选答案字段的组合 | 可在 Today 排期、撤回及确认实际；来源可追溯 |
| 参考摆放 | 答案与行动旁或独立时间位置的关联 | 不自动生成完成事实或消费长期资源 |

抽取草稿、已拿出的素材和长期原卡分开。单次点击、翻面、取消或预览不偷偷新增手牌；明确取牌或接受才保存。合成预览不消耗素材，确认成功才原子替换两张素材。已消耗素材不能再被另一合成使用。

这里的“参考”是选择结果的展示用途；既有事实追加批注继续遵守不可覆盖规则，不把两种用途混成同一项可随意修改的历史。

## 4. 通用收纳与候选

- 独立牌堆可只承担清单功能，不需要虚构行动卡、决策卡或生成规则；空清单也允许存在。
- 工坊支持建立清单、维护条目、调整成员与顺序、移动条目及查看内容。文字名称是共同展示基础；领域补充字段按合同扩展，不要求书、食物、网址共享全部业务字段。
- 多个决策可以引用同一候选牌堆，引用关系不转移其所有权；取消绑定后清单与成员仍在。
- 书从待读移到已读是用户明确的整理动作。完成一次阅读不自动宣告全书读完；旧手牌、答案与阅读事实保留当时快照。
- 项目清单条目在本版属于收纳内容，不等于交付目标管理、项目成果验收或完整项目管理系统。
- 沿用每个牌堆最多 100 个直接成员的现行边界；不增加全库牌堆、条目或历史总量上限，不裁剪个人数据。

## 5. 页面与用户路径

### 5.1 全局手牌浮窗

固定右下角入口展示本次手牌与数量，展开后可以查看行动、答案与合成牌，保留来源和区别。页面切换保持同一份权威手牌；浮窗位于应用装配层，避免每页各养一份可写状态。

非 Today 浮窗只预览，不提供打出或绕道写入安排的交互。工坊的拿牌和合成是工坊独立操作，结果更新浮窗；它们不让浮窗在工坊变成第二个编辑入口。Today 提供打出、撤回和现有实际确认。窄屏可调整展开方式，保留可见入口、关闭、键盘和焦点返回。

### 5.2 行动抽卡页

沿用球体、两步翻牌与静止替代路径，补齐勾选牌堆的候选范围。选择范围与接受的具体卡保持一致；未选、空堆或没有可用候选显示可理解的空状态。原每日库存、补日、重复接受与七天来源边界继续验证。

### 5.3 决策抽卡页

矩阵展示问题卡，用户明确触发抽取后翻出具体答案；普通渲染、导航和重开已保存手牌不再次抽取。允许主动重抽、手选和取消。答案与问题、条目、牌堆来源一致，不能只显示一个随机名称而无法回到其收纳内容。

直接进入此页时可以只取得答案，也可以明确选择同时拿出对应行动牌；两种路径都可用，不把一次随手询问悄然变成待做行动。默认按钮布局待 C0/A0 核对。

### 5.4 工坊与三槽合成台

矩阵统一提供行动牌堆、决策牌堆和独立收纳牌堆入口。放入一张本次行动素材与一张已选定答案的决策素材，第三槽预览具体结果；确认后两张输入被一张结果替代。结果继承正确字段及来源，长期定义不被覆盖。多张附属决策可分步合成，后续合成须保留先前已继承内容。

同名字段、不同决策来源或重复素材的合成冲突须在预览中解释，不静默覆盖。取消保留两张素材；失败保留可重试的本次操作，不出现少一张输入或多一张成品。

### 5.5 Today 的参考牌

默认把答案贴在相关行动旁，共用该行动的安排；不能把同一安排再计一次占用或执行时长。允许独立参考位置，具体定位与占用规则须在 C0 冻结后才写入正式时间模型。单独摆放答案不生成“已吃饭／已阅读／已锻炼”的事实。

行动与参考在刷新、跨日查看和恢复后可以对应。来源改名、条目转移、决策原卡修改不反向改写已确认记录。

## 6. 同级验收场景

| 用例 | 相同框架必须走通的路径 |
| --- | --- |
| 阅读 | 抽读书／工坊拿读书 → 从书目抽具体书 → 答案参考或工坊合成 → Today 使用 → 确认实际；明确读完全书后移动牌堆 |
| 吃饭 | 抽吃饭／直接决策 → 从餐食条目抽本餐答案 → 参考或合成 → Today 使用；参考与午餐共用安排，不重复占时 |
| 锻炼 | 抽锻炼／工坊拿锻炼 → 从项目条目抽具体锻炼项目 → 参考或合成 → Today 使用 → 确认实际 |
| 独立清单 | 创建未绑定任何卡的零食、网址或项目清单 → 维护与移动条目 → 刷新／导出／恢复仍保留；后续可以明确绑定决策 |

三种生活用例只换用户配置的数据；核心流程与命令共用。上述例子仅作为隔离合成测试输入，不预装为用户卡包，不通过新增三个独立功能页完成验收。

## 7. AI 批量配置

交付正式字段说明、有效空包与最小框架样例、外部 AI 生成提示词、独立校验入口及可理解的错误反馈。样例同时覆盖三类用例与一个无绑定清单，仅供生成和验收参考。

配置包覆盖可复用定义、牌堆、条目、决策归属与字段映射；不生成用户已完成事实、私人日记或虚构执行历史。导入先校验及预览，再明确确认；新增、修改、停用和绑定变化可理解。稳定 ID、重复导入、未知字段、缺失引用、超限和失败原子性须验收。

当前 ConfigV3 不含这些新增概念，不能伪称已有批量导入能力。新包格式、旧包兼容与迁移由 C0 设计；不借配置导入替代完整备份恢复。

## 8. C0 必须冻结的实现边界

下列包含尚待决定的卡牌默认方案，以及已定记录路线中待具体化的实现边界。第 11 节的简化路线已获用户确认；C0 须给出具体样例、方案理由、容量证据和最终接口，不能把已确认路线重新当作待选项。剩余会改变业务意义的取舍向用户聚焦确认，不让两条线各自猜测。

| 事项 | 建议方案与约束 |
| --- | --- |
| 独立答案的时间位置 | 默认作为时间点参考，不新占执行区间；若需独立占时，先定义时长、冲突与计数，不能当作已完成行动 |
| 消耗状态 | 合成只接受未打出的本次素材；已排期素材先在 Today 撤回。已有事实拒绝重新合成或改写 |

| 到期与来源 | 旧每日来源规则保留，合成不能洗掉期限；建议结果继承输入中最早的到期边界。常驻手动素材不凭空新增七天期限 |
| 参考与事实的关系 | 明确关联对象、删除／撤回后的显示及事实确认时保存的参考快照；已确认事实不能追随可变目录漂移 |
| 格式版本 | 建议 Envelope v4 保持，新增 Data v5／Backup v5／Config v4，精确号数与字段经 C0 冻结；旧 Data v4 不偷加字段 |
| 泛化旧书目与槽位 | 建立可核对映射，保留现有书目、池、规则、手牌和日记；不静默改释义或丢失版本来源 |
| 时间线日记 | 区分行为区间、随记原时间及后续修改时间；自动段按 P13 镜像表盘，随记按 P16 独立保留，睡眠按 P18 读取表盘。冻结跨日、未来安排及历史时区的显示；日记文字不自动等同已确认事实 |
| 纯文本文件 | 按 P15/P17/P19 实际生成、单向更新；在写入、重连或主动刷新时检查外部改动，不持续监控。冻结目录、命名、后缀、失去权限及最近成功输出识别；建议恢复前另存改动副本。正常更新与外部改动须区分，不能因文件暂未更新就回滚正常操作 |
| 文件与工作区的一致性 | 浏览器工作区提交与用户目录写文件不能假设是一个原子事务。建议主数据保存后排队生成文件，记录待同步状态，失败可补写；序列化与版本核对防止旧输出覆盖新内容，多窗口与工作区替换纳入验收 |
| 维护日志与日记容量 | 现有 5 MiB 同时限制普通保存与恢复；日记历史包含整篇前后快照。已定路线是技术日志独立存储、感想按条目变化，先验证并适度调整统一容量门槛，复用 JSON 主备份。长期正文仍会增长；数值和验证规模由 C0 给出。若现有存储不达标再审必要分区，不提前做分库／分片或删旧历史 |

## 9. 完成标准与边界

1. 三类生活用例与独立清单均通过真实生产路径；切换领域仅更换配置，不改代码。
2. 浮窗跨页一致，非 Today 无打出入口；Today 原计划、事实、批注与日记保存边界不回归。
3. 决策结果稳定、可取消和明确重抽；无候选、失效条目、过期素材和多窗口更新能正确反馈。
4. 合成原子替换两张素材为一张成品；重复提交、丢回复、并发消耗、失败重试与工作区替换均无半成功。
5. 独立牌堆无需绑定即可使用，多个决策共用候选；转到已读清单后历史来源快照仍可解释。
6. AI 配置、完整备份、旧格式精确恢复和显式迁移分别验证；个人真实数据不自动处理。
7. 320／390／720／1280px、键盘、减少动态效果、空白与拥挤日可操作；生产离线更新保留工作数据。
8. 作者回归与非作者分离验收分别记录，后者通过前不宣称版本已验收。
9. 日记自动段随放置／移动／收回实时更新；独立随记保留原时间和修改标记，行为撤回不删感想；睡眠复用表盘时段。
10. 日志记录应用内操作与清单发起的网址打开；真实文本文件可重开读取。外部改动按 P17 恢复，文件失败可补写，正常更新、恢复和多窗口不造成旧文件覆盖新内容。

本版不交付云同步、在线 AI 服务、营养／训练专业推荐、目标项目完整管理、自动完成判断或大规模个人数据清理。实际产品版本在发布收尾才改为 0.6.0；本次策划不授权提交、推送或自动迁移。

## 10. 维护日志与时间线日记

### 已明确的用途

日志主要给系统维护者看，用户一般不主动查看。范围已通过本轮回答确定为 CardGrid 内操作和从清单打开的网址；应可转换为 Markdown 纯文本。现有成功业务命令的前后历史可以复用，页面进入、链接打开和失败操作等还需补齐记录；原每日副本归档日志不是这项能力的替代。

日记是生活时间线：表盘上的睡觉、行动、吃饭等行为时段实时带入；用户随时写下的话自动附时间戳。比如原本 06:10 写的内容，08:15 修改后仍属于原来的时间位置，另外标注 08:15 的修改。日志与日记实际生成纯文本文件，使用 Markdown 组织内容即可通过 `.md` 后缀被相应软件识别。

每日感想是独立记录：早餐收回，自动段消失，但“今天早餐很好吃”的随记继续保留其原时间戳。不能把随记建成某个可撤回安排的从属正文而级联移除。睡眠来自已有表盘安排，例如 00:00—06:00；用户调整它，日记跟随，不从空白时间或打开应用的时刻推断睡眠。

用户先对编辑方式回答“1.2”，进一步访谈后明确改为**不做双向同步，外部修改导致不同时退回上个版本**。按上下文这是恢复日记／日志文件到最后一次成功生成的内容；外部文件不回写计划、事实、感想或工作区。应用内正常编辑、排期改变仍产生新版本。检测依据应包含最后成功写入的指纹和源版本，而不是只比较当前工作区和暂未更新文件的字节。

早餐放到 08:00 就生成一条 08:00 记录，移到 10:00 就更新同一条为 10:00，收回则从日记正文移除。日记表达当前表盘安排及个人文字，不需额外确认才记入；维护日志保留创建、移动和撤回的过程。这是可调整安排的展示规则，不能据此解锁或删除既有已确认事实。记录文字的原时间、当前行为时间与修改时刻是不同概念。

当前 v0.5 只存一天一篇 `text`，只有整篇的创建和修改时间，并没有逐条随记时间、行为关联或自动更新段。新能力需要扩展条目与展示，而不是在旧正文末尾反复追加字符串。

### C0/A0 需具体化的细节

1. 自动行为按区间展示，独立随记按原记录时间穿插；修改默认显示最新修改时刻，维护日志保留操作过程。不先增加完整修订正文浏览器。A0 核对随记输入与编辑是否易懂。
2. 建议一天一个日记文件、一天一个维护日志文件，分目录存放，正文按 Markdown 排列；目录、后缀选择与重连在设置中提供，不为维护日志新增高频使用的主页面。
3. 跨午夜按日展示行为片段并保留同一来源；历史日期与时区不重写。未来安排可否生成未来日记文件、随记补写／清空沿用哪些 v0.5 规则，在 C0 记录具体方案；影响已定业务意义才向用户确认。
4. 旧日记整篇迁移为旧正文块，保留全文及原整篇创建／修改时间，不凭空推算每句话的时间戳；旧完整备份仍能精确恢复。
5. 维护日志以具名用户操作、自动业务结果和错误为基础，例如页面切换、清单打开网址、抽取、合成、排期及保存；打开网址记录发起打开和目标，不假称已读取外部页面及其后续操作。具体粒度和完整覆盖清单由 C0 给出，不把每次渲染当成一次用户行为。

### 架构建议，尚待 C0 冻结

保留已有计划、实际和成功命令历史，增加按条目的时间线随记与维护日志采集。业务数据及记录保持同一次正式提交；日记从行为记录和用户随记组装，Markdown 按固定规则生成。维护日志与用户日记用途不同，界面与输出分开，不能把所有点击轨迹混进生活正文。

系统自动段与可改写文字需要明确归属。建议一次行为保持稳定关联，变更更新该行为的展示并附修改时间；用户原文字不被自动重新生成覆盖。这里的“从记录组装页面”就是投影：同一份来源生成不同用途的可读结果，不要求重写成完整事件溯源系统。

每条行为和随记需要稳定身份；时间戳负责显示、排序及修订标记，不能独自充当唯一标识。两条内容可能同一分钟产生，行为时间还会从 08:00 改到 10:00；把时间当身份会使同一条记录被误认成删除加新增。文件不回写后，不需要解析任意外部 Markdown 来重建业务身份。

现产品存储为浏览器 IndexedDB，并没有后台本地文件服务。用户目录实际写入可先采用受支持浏览器的目录／文件授权接口；需要用户选择位置并授予写入权限，权限不保证永远有效，不能假设网页可任意写磁盘。目录连接、文件失败和恢复后补写的产品反馈须明确，失去授权时保持主数据与随记，提供重连和重试。能力依据见 [Chrome 官方文件访问说明](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access)；C0 核对支持范围与降级方案。

以上核心愿景已进入完成标准与并行计划。接口、容量、故障和兼容映射经 C0/P0 冻结后开发；不增加富文本、附件、统计、自动生成个人感想或在线 AI。既有已确认事实与可改写日记的区别继续成立，改变其规则时需说明影响并由用户决定。

## 11. 降低首版开发复杂度的方案（已确认）

确认日期：2026-10-06。用户在阅读简化方案后回复“可以”，本节路线成为 v0.6 策划基线。C0 继续准备样例、容量验证与具体接口；路线确认不等于接口已经冻结、代码已经开发或个人数据已经迁移。

| 范围 | 已确认的首版路线 | 减少的工作 |
| --- | --- | --- |
| 日记自动段 | 直接读取正式表盘的计划／固定安排／事实，按来源投影为时间线；不再存另一份自动段 | 不需同时维护两套行为数据；移时／收回自然跟随表盘 |
| 个人感想 | 在现有工作区增加独立条目，保留稳定 ID、原时间、修改时间和文字；保存历史针对单条变化 | 不反复复制一整天的日记，也不因撤回行为而连带删文字 |
| 文本输出 | 日记与日志共用一个文件输出端口；界面即时更新，文件短暂合并更新后按天生成完整文本 | 不做 Markdown 回读、段落合并或逐字符增量写入；一次写失败可重试整份当日输出 |
| 外部改动 | 在文件写入前、重连或用户主动刷新时核对最近成功输出；发现外部修改则保留改动副本，再恢复最近成功内容 | 不持续监控磁盘；代价是外部改动不会在修改瞬间被发现，应用检测到时才恢复 |
| 维护日志 | 成功业务操作复用现有历史；额外页面／网址打开／失败记录在现有本地数据库的独立存储区，和主工作区分开；按天生成日志文件 | 不另建数据库服务，不把所有技术操作塞进工作区对象；不为原本已有的命令再复制一套业务快照 |
| 备份与容量 | 主备份保留现有 JSON 路径，包含全部业务数据与日记；维护日志文件单独管理。先核对并适度调整容量门槛，不提前做分库、ZIP 或分片备份 | 保持既有备份／预览／恢复链路；降低格式和恢复算法的变化范围 |
| 旧日记 | 整篇保留为旧正文块，新感想按新条目记录 | 不自动拆段、不推测历史时间戳、不要求用户手工重新录入 |

容量策略仍须用代表性历史数据验证保存、读取和恢复耗时、内存及失败行为。当前 5 MiB 同时用于普通写入、导入后状态与恢复检查；它不是单独的导出文件限制。C0 应区分输入文件保护和工作区容量，保留可恢复的边界并同步所有入口，不能只改一个导出常量或承诺无限容量。如果现有存储在所需规模下不能达标，再提出必要的分区方案，不因“简化”取消一致性和恢复验证。

本版不新增自动清理或日志打包。技术日志保留在独立存储区与输出目录，由用户管理，不随普通业务主备份混入；完整业务与日记恢复能力不可缩减。C0 必须在备份说明与恢复样例中明确这一已确认范围，不再要求用户重复选择。具体自动清理期限没有被指定，不能擅自设为 30／90 天或静默删除。

共用文件端口仍必须处理串行写入、多窗口、epoch 替换、最近成功快照与失败补写。它隐藏这部分工程细节，供日记和日志调用，不要求两个模块各做一套。文件是否已经写入成功单独反馈；主数据保存成功不因文件失败而撤销。

### 12.1 三组待确认的业务默认值

| 编号 | 具体场景与候选结论 | 理由及影响 |

| F3 未来与补记 | 未来表盘安排可读，并生成标为“计划”的未来日记自动段及文件；**个人随记继续禁止写未来**，可补过去。补记的归属日是选择的过去日，原记录时间是实际写下的时间，显示“补记于完整日期时间”，不伪造过去时间。旧正文及新随记可清空，保留 ID／时间／历史，不增加整条删除 | 保持 v0.5 自由文字的日期与清空边界；允许用户看见已安排的明天，同时区分计划和已发生事实 |

这三组获用户确认前，不把它们写成已冻结产品决定，不开启新持久化。默认按钮为“只取答案”；“同时拿行动牌”为独立明确操作，同一提交原子生成两张素材；取消、翻面和预览均为零写入。

### 12.2 身份、目录与本次牌

以下是字段合同；P0 才发布对应 TypeScript 类型和运行时校验，不在 C0 向生产 Command 联合类型添加空实现。

| 对象 | 必备字段／约束 |
| --- | --- |
| 通用条目 CatalogEntry | `id, version, title, attributes, url:null|string, status, source`。title 非空；attributes 为平面键值表，值仅 `string/finite number/boolean/null`，不接受任意脚本、嵌套对象或数组；保留原 author 的 null 与缺失差别。URL 为经校验的 http/https 地址 |
| Deck | `id, version, name, deckKind:action|decision|entry, parentDeckId:null|Id, memberIds, source`。同种类成员；同种类父堆；无循环；成员顺序有意义、不重复。每堆最多 100 直接成员，归档条目计数，子堆不合并。空 entry 堆、无任何绑定的堆合法 |
| ActionCardV5 | 保留原 `id/version/content/status/parentId/source`，以 `fields:[{id,label,valueType:text|number|boolean,required}]` 表达预留字段。卡内 id 与模板 label 唯一。模板只替换一次，不递归展开条目中的花括号 |
| DecisionCard | `id,version,question,ownerActionId,deckIds,mappings,status,source`。单张决策恰好一个行动原卡归属；一个行动可有多个决策。候选堆为 entry 种类，可被多个决策引用；并集按条目 ID 去重。mapping 为 `fieldId + entryPath(title 或 attributes.<key>)`，类型须与行动字段相同；不允许映射身份、时间、事实、奖励或整个 Content |
| AnswerSnapshot | 问题、决策版本、行动归属、候选条目版本及完整展示快照、候选来源堆、映射结果、选择时间。手选／随机一旦确定即固定；重渲染不重抽，主动重抽是新的会话选择 |
| HandCard | `id,version,kind:action|answer|composite|entry,state:available|consumed|expired|withdrawn,createdAt,actionInstanceId:null|Id,ownerAction,contentSnapshot,fieldValues,provenance,inputIds,expiresAt:null|Instant,consumedBy:null|Id`。时间戳和名称均不当作 ID。entry 牌可预览、打开 URL；不能直接排为执行行动 |
| ReferencePlacement | `id,version,answerId,mode:attached|point,targetInstanceId:null|Id,point:null|RecordedPoint,createdAt,changedAt,state:active|returned|expired`。attached 必须与行动来源一致；point 带 UTC instant、zone、localTime、offset，DST 重复时间显式选 offset；不使用零长度 Plan 假装区间 |
| FactReferenceSnapshot | 以 `factId` 关联事实，在 ConfirmActual 同一事务保存当时已贴附答案的完整快照；旧事实不补造快照。原 Fact 字节和追加 Annotation 规则不变，不往旧事实里补可变目录指针 |

直接拿同一原卡两次得到两个 ID。行动未补齐时只作为 HandCard 素材；完整成品接入原 Instance／Plan／Fact 链。已有 Instance 通过明确的来源映射关联素材，合成时不能删除旧 Instance：无事实输入退出可用手牌并记录消费；普通 ReturnWithdrawn 不得复活已消费输入。旧手牌无法可靠推导行动来源时保留原使用能力，拒绝猜测其合成归属。

合成预览绑定 token、两输入 ID／version、归属原卡版本、字段方案和源指纹。确认时重新校验；同一个 ID 放入两个输入槽、已附着参考或独立摆放的答案均拒绝。原值为空时填入；值及类型相同可合并来源；不同则逐字段选择。新成品保存所有直接输入及递归来源摘要，不覆盖原库。字段不完整的中间结果必须显式提示“待补全”，不能伪装成可打出的行动。

到期计算比较 **UTC 时刻**，不能只比较不同规则时区下的来源日字符串。日副本 D 在其冻结规则时区的 D+7 00:00 到期；本次拿出不能重新计算 D。常驻手动素材为 null；合成取所有非 null 的最早值，全部 null 则仍为 null。到期按原七天协调入口归档，撤销未完成排期／参考、移出活动手牌，消费谱系、事实、批注和随记保留。

| 旧手牌与事实 | Instance、创建来源、Plan、Fact、Annotation、旧历史、回执逐项保持；可核对 daily.copyId 来源才建立 catalogAliases／素材映射；不把旧组合当成新答案重新抽一次，不补造参考事实 |
| JournalEntry | 保留每篇 ID、version、date、zone、全文 text、createdAt、updatedAt，包括空正文、CRLF、空格和旧全文历史；显示为“旧正文块”，不拆段、不推算句子时间。新 journalNotes 与旧块分别编辑，旧正文修改的历史只针对该块 |
| Data2/3 与旧配置 | 继续现行识别、读取、备份及显式迁移；完整备份按原版本恢复。旧 ConfigV3 可在只读预览中映射到 Config4，列出自动产生的决策与字段，确认前不写入。旧引用失效／槽标签歧义属于阻断问题，不自动解绑 |

Config4 只含可复用定义：settings、definitions、templates、rules、actionCards、catalogEntries、decks、decisionCards、generationRules；不含 HandCard、库存、参考位置、事实、回执、私人日记、日志、文件句柄或文件队列。未知字段／版本、不合法引用／类型、同 ID 种类冲突、超百全包拒绝。目录和候选移动不改已接受快照；重复同内容配置不重复新增。

Backup5 包含全部业务与日记，也包含原旧正文及旧历史；不包含 maintenance、文件句柄、输出队列、授权或最后输出缓存。精确恢复指 data 的属性有无、null、数组顺序、全文及版本保持，外层 epoch 依法更新；不能要求恢复旧 envelope token。恢复 v4 后仍为 v4，不偷偷升级；升级要先完成可下载的精确备份证据、只读迁移预览，再明确 CommitMigration。预览要包含变更清单、别名、字节量及阻断问题。

### 12.4 时间线、随记与旧正文

自动段来源是正式 readDay 的活动计划、固定安排（含未实例化的模板投影）与事实；不从标题猜睡眠，不从空闲推测行为。睡眠就是表盘已有固定／计划来源。计划与事实分状态展示；确认后实际段为事实，原计划作为同一行动内的“原计划对照”，不生成第二次生活行为或计时。

稳定来源键：行动为 `instance:<id>`，固定安排为 `fixed:<id>`，未落库模板为 `template:<templateId>:<version>:<date>:<entryId>`。同一来源跨午夜可切两个片段，片段键包含日期／时区，但来源不变；移时更新位置，撤回移除活动计划段。浏览、切日、渲染不创建数据或文件任务；正式业务变更才标记受影响日期。既有事实保持可见、不可撤回，不能因某张原卡停用而消失。

JournalNote 字段为 `id,version,kind:'reflection',date,zone,recordedAt,createdAt,updatedAt,text`；ID 为独立生成，初次创建 recordedAt=createdAt，后续不可改写；修改只改变 text／version／updatedAt。没有可撤回 Plan 外键；可选展示关联不参与级联。新空白不建档，已有条目清空仍保留，不重设原时间。日记日期、未来禁止、自动保存防抖／排空、失败留草稿、切日与离页保护继续复用 v0.5。

新保存历史记录单条 before/after，不复制一整天。旧历史只保留，不压缩、重算或删除。新旧正文可同时展示；按行为开始时间、随记原时间稳定排序，同刻按类型与 ID 排序；旧正文块单列“历史正文”并显示原整篇创建／修改时间，不混入虚构时间线。

settings.zone 决定今天与默认新记录时区；UTC 范围、本地快照、随记归属日及其原时区不会因设置改变而重写。跨时区同日的所有个人文字均可见并标注时区。自动段通过 readDay(date, zone) 换算为当前查看时区，明确展示 offset；文件以 (date, zone) 区分，同一来源的跨日片段和未来计划明确标记。时间显示和数据身份分开，DST 不按 1440 分钟硬切。

### 12.5 容量候选与本次证据

原集中存储路线的候选工作区门槛为 **32 MiB**（33,554,432 UTF-8 字节），尚未冻结，当前须结合第 13 节重新选择。按包含 format/version/kind/dataFormat/data 的紧凑 JSON 主备份计算；等于门槛接受，下一字节拒绝。输入原文件保护候选为 **64 MiB**：文件选择先检查 File.size，读取后解析再检查输入字节；允许合理格式化空白，但导入／恢复／迁移后的工作区仍须受工作区门槛约束。两者不是条目数上限，也不是保留年限。

容量探针与共同样例见 [v0.6-c0](../开发/v0.6-c0/fixtures.mjs)，运行说明及最终结果见[计划第 11 节](../开发/2026-10-06-v0.6并行开发计划.md#11-c0-本轮执行记录2026-10-06)。一年模型为 365 天、每天 4 条 180 汉字随记、每条一次修改，6 个行动及各自拿牌／排期／确认历史和回执，另含 10 堆×100 条目：紧凑备份 **19.87 MiB**。三年同频率模型 **59.39 MiB**，超过候选 32 MiB；它是明确的限制样例，不能说三年已获容量保证。完整新格式和 Host 性能仍需 B4 正式验证。

当前 v4 纯日记控制组（一年、每天四段文字、八次整篇保存）已达 **8.92 MiB**，旧 5 MiB 解析门槛拒绝；这证明全文重复历史有实际容量成本。新条目策略不能消除行动快照与回执的增长。进一步对带相同行动／计划／事实数量的合法 v4 控制组运行现有完整 validateActionData：一年 **3.49 秒**、三年 **13.89 秒**；这是纯校验，不含 Host 提交，不能用较快的 IDB put 探针冒充普通保存性能通过。仅放大字节常量尚不足以放行。原 24 MiB 提醒／32 MiB 拒绝仍是集中路线候选；禁止自动截断、清理或把主备份漏项来通过门槛。

本轮没有修改任何生产门槛；正式落地须统一 `workspace/format.ts`、`commands.ts`、`client.ts`、`migration.ts`、`app/App.tsx` 的保存、导入、迁移、恢复、诊断和可恢复备份判断，以及所有文案。在读取和导出时不裁剪超限旧数据；已有超限只读记录仍可完整诊断导出，恢复超出正式门槛则明确拒绝，不虚称可恢复。24/32/64 MiB 边界、UTF-8 多字节、完整旧恢复反例进入 P0/B4 门禁，原断言改为引用明确的新合同，而非删除容量测试。

技术日志和输出缓存有各自的字节状态及浏览器 quota 检查，不计入上述主备份预算。不设自动保留天数、不自动清理。**同一个 IndexedDB 的不同 object store 仍共享浏览器配额**；独立存储区只能避免技术日志触发主工作区 32 MiB 校验，不能承诺它永不造成 QuotaExceeded。实际配额不足时保留原库、提示用户处理空间，不自动删除任何历史。

### 12.6 维护日志采集与恢复范围

语义事件包含 `eventId,epoch,at,date,zone,category,operation,stage,result,commandId:null|Id,sourceHistoryIds,entityRefs,errorCode,details`。成功业务从 planner.history 派生；同 commandId／historyId 重放不产生第二次用户操作。可缓存精简文本行以保存跨工作区替换的维护线索，不复制完整 before/after 业务快照或日记正文。额外事件写入独立 maintenance 区；技术日志失败单独反馈，业务已提交不得报成业务失败或诱使重交。

| 覆盖 | 粒度 |
| --- | --- |
| 页面与生命周期 | 实际进入／切换页面一次；启动、离线重开、显式工作区恢复／清空／迁移、文件连接／断开。重渲染、鼠标移动、读取和普通日期浏览不记成业务变更 |
| 工坊与抽取 | 明确保存／导入／移动成员；明确拿牌、发起抽取、手选、主动重抽、接受、取消；纯翻面可以记录会话阶段，但不假造行动接受 |
| 合成与 Today | 预览、确认及拒绝；排期、移时、撤回、固定解锁／更改、实际确认、追加批注、参考摆放／收回；成功以历史／回执为准 |
| 日记与错误 | 条目创建／修改／清空及保存失败，只记 ID／版本／字符数／错误码，不把感想全文放进技术日志；重试阶段关联同操作 |
| 清单 URL | 记录条目 ID、用户明确请求的目标 URL、发起时间以及浏览器反馈。只能声称 open-requested／blocked／failed，不声称外部网页已加载或读到了后续操作 |
| 文件输出 | 待写、失权、失败、补写、检测到外部修改、保留副本、恢复与核对结果；不把每次轮询写成操作，不持续监控 |

维护日志按 epoch／date／zone 分日保存；旧 epoch 不删除。主备份恢复不导入或清空 maintenance；原日志文本独立保留。历史成功业务可由现有历史解释，但旧版本没采集的页面／URL 行为不能补造。额外事件存储失败保留本会话重试信息并显示缺口，不能保证浏览器崩溃后未落库事件仍在；这是必须暴露的降级。业务和技术日志的恢复边界在设置及备份说明分别注明。

### 12.7 共用单向文件端口与故障规则

接口能力基于[Chrome 文件访问文档](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access)和 [File System Access 规范](https://wicg.github.io/file-system-access/)：目录选择／请求授权由用户手势触发，句柄可保存在 IDB，授权需重查；不能依赖外部文件 rename/move 的普遍支持。首版完整自动落盘要求检测到 showDirectoryPicker、可写句柄及 Web Locks；Chrome／Edge 桌面作为正式验证对象。不支持时提供明确“未连接／浏览器不支持自动写入”与手动下载，不冒充已完成 P15 的实际同步。

路径为用户选择目录下的 `CardGrid/<bindingId>/<epoch>/journal/<encoded-zone>/<YYYY-MM-DD>.<suffix>` 和同层 `maintenance/...`；suffix 为 md 或 txt，UTF-8、LF、Markdown 内容。encoded-zone 不允许路径分隔符逸出；bindingId 为本机稳定输出连接身份，JSON 主备份不携带。每个日期／时区一份完整文本，日记与维护日志分目录。切后缀或目录新建明确连接版本并重新排队，不静默删旧文件或依赖文件移动。旧 namespace 保留供用户管理。

FileBinding 保存目录句柄、bindingId、connectionVersion、suffix、活动 epoch。OutputKey 为 `bindingId/connectionVersion/epoch/kind/date/zone`。每个文件保存 lastSuccess（完整成功文本、SHA-256、源版本、成功时间）和可持久恢复的 writeIntent（目标文本／指纹／源版本／阶段）；两种文本共用一套队列与状态存储，均不进入主 JSON 备份。

源版本分别是工作区 token 加渲染输入指纹、maintenance 日分区修订号。业务成功后标记受影响日：移时跨日同时更新旧日和新日，撤回最后一项时把曾存在的输出写成明确空内容，不删文件。队列按 OutputKey 合并，约 500 ms 后完整重写，active 写入完成后再取最新源，重试不重复执行业务命令。崩溃在业务提交后、排队前时，重开／重连从源版本与文件清单重新识别脏日期，不依赖只存在内存中的通知。

| 故障／竞争 | 确定处理 |
| --- | --- |
| 正常更新尚未落盘 | 磁盘等于 lastSuccess 即正常旧版本；不与当前未写入内容直接比较为“外部修改”。业务仍已保存，文件显示 pending |
| 外部内容改变／文件缺失 | 仅写入前、重连、主动刷新检查。内容改变先按原字节另存 `conflicts/<安全文件名>.<检查ID>.external.<suffix>`，成功后恢复 lastSuccess，再写当前最新输出；缺失则重建 lastSuccess 再更新。不是回滚工作区 |
| 首次连接已有同名文件 | 尚无 lastSuccess 不能称为“恢复上个版本”。先保留原文件副本再初始化当前输出；副本失败则暂停，不覆盖未知内容 |
| 保留改动副本失败 | conflict-copy-failed，保留外部原文件并暂停本文件；不先覆盖再尝试备份。其他文件可继续，业务数据不回滚 |
| 权限丢失／目录失效／磁盘失败 | permission-required 或 failed，待用户手势重连／重授权，保持最新待写源；不可后台反复触发授权弹窗。网络离线本身不阻止有权的本地写入 |
| 多窗口 | 通过[Web Locks](https://www.w3.org/TR/web-locks/)持有同一连接的独占写锁，锁内读取权威源与输出状态；仅 BroadcastChannel 通知不足以防竞争。无锁能力时自动同步暂停。不能假称同源锁能锁住其他浏览器或外部编辑器 |
| 源版本变更 | 尚未开始的旧任务丢弃／合并；正在写的版本可短暂成为文件的成功旧版本，随后写最新源，状态仍 pending。串行锁保证较旧任务不能在较新成功输出之后再覆盖它；逐文件持久状态用版本条件更新 |
| epoch／连接版本替换 | 未启动旧任务失效；已启动任务只能触及其旧 namespace，不能写新 epoch 目录或更新新连接状态。恢复／清空／迁移后文本同步暂停，明确选择“继续为此工作区生成”后再启用；不恢复旧句柄授权、不删除旧文件 |
| close 成功但状态提交失败／崩溃 | 先持久化 intent，再写并 close，读取核对实际字节后推进 lastSuccess。重连发现磁盘匹配 intent 且连接／epoch／源核验成立，则补提交成功状态；仍匹配旧 lastSuccess 则重试；其他内容走外部改动分支。不能把这种间隙当成用户篡改并直接覆盖 |
| 写入／核对失败 | lastSuccess 不前移；retain intent，状态 failed 或 reconcile-required，重试前先核对可能已成功的磁盘内容。数据库和文件不是一个原子事务，不宣称严格 exactly-once 落盘 |
| 主动刷新 | 检查已有清单、恢复外部改变、排空当前 dirty 文件；不从目录扫描任意 Markdown 导入工作区，不做持续文件监控 |

状态端口提供 `unsupported/disconnected/idle/pending/writing/synced/permission-required/failed/conflict-copy-failed/reconcile-required/paused-after-replace`，以及 OutputKey、源版本、lastSuccess、待写数、错误和恢复副本位置。synced 仅在 close、字节核对及成功状态持久提交后报告。主数据和文件各有状态，不把文件成功掩盖为数据保存成功，也不反向撤销已提交业务。

文件 API 无法与外部编辑器构成同一事务；读后到 close 之间的外部竞争仍可能发生，写后核对及下一检查需处理。首版不承诺瞬时发现或任意外部程序并发下的无损合并。真实目录授权、权限撤销、保留副本、close/状态间隙和重新连接须在 B9/I2 实验，当前探针没有验证它们。

### 12.8 端口、错误及 P0 退出条件

以下为 P0 名称与职责候选；类型文件、DTO 精确联合类型、格式分支和可替换测试适配器在 P0 发布。正式具名命令统一带 `commandId + expected Token`，版本引用不可用名称替代；变更、消费、输出引用、历史与回执同事务。预览无写入，取消为会话退出；失败重试沿用原 commandId／payload，改变草稿必须新建 commandId。

| readCatalog / readDeck | token、过滤／deckId → 严格目录快照、有效候选及停用原因 | SaveCatalogEntry、SaveDeck、SaveActionCard、SaveDecisionCard、MoveDeckMember（两堆原子） |

| readUnifiedHand | token → 各类本次牌、可打出／待补全／已过期原因、来源 | 活动原行动复用现有 ReorderHand；新种类排序精确接口在 P0 对齐，禁止复制第二份可写手牌状态 |

## 13. 月度归档与多压缩包只读浏览（用户新提案，待设计确认）

2026-10-06 用户在容量结果后提出：每个月提示导出一次该月数据，导出后清除，支持多个压缩包导入进行只读查看，通过分段转移内存压力。**可行，并值得作为集中历史持续增长的替代路线；当前是设计评估，不是清理授权或已实现功能。** 这是用户主动提出的新方向，允许替代第 11 节的“不提前分片／ZIP”边界，但不能自动认定备份合同和只读限制已经获确认。

关键不是 ZIP 的压缩比，而是“当前工作集＋月度归档”。ZIP 缩小文件体积；读取时若全部解压再合并进当前 Data，内存与整库校验问题仍在。多个包应进入独立归档区，只建立小型索引；看某月才加载该月数据，离开后释放，跨月查询最多保留明确数量的月份。归档格式可采用 manifest.json＋records.json 的普通 ZIP，之后需要时可按集合拆文件，但不先扩展 ZIP 分卷、云同步或完整归档编辑器。[zip.js 官方项目](https://github.com/gildas-lormeau/zip.js)提供浏览器流式 ZIP 能力；尚未选定依赖、安装或验证 ZIP 实际路径。

### 13.1 建议用户流程

1. 次月第一次打开应用时提示“上月可归档”，也可主动归档；逾月未打开不丢数据，下次提示未归档月份，不承诺浏览器关闭时提醒。提醒不自动删除，也不阻止日常操作。
2. 预览可归档的记录数量、日期／时区、体积和仍被当前工作引用的项目；以权威快照 token 和源指纹固定本次范围。
3. 导出 `CardGrid-<workspaceId>-<YYYY-MM>-<archiveId>.zip`：包含该月日记全文、已封存行动／计划／事实／批注／相关历史，以及解释它们必需的目录版本快照、格式号和校验清单；维护日志仍明确独立，不能混淆业务备份。
4. 对实际保存的包重新读取、核对 hash、格式、全部引用和只读呈现；普通浏览器下载不能直接证明用户硬盘上的包可读，需要重新选入验证或使用已授权目录读取。只在包可独立解释、清理预览仍与当前 token 一致、用户明确确认后，从活动区移出对应记录；事务失败则活动区原样保留。
5. 一次选择多个归档 ZIP，逐包校验并登记压缩 Blob／句柄与小型月份索引。查看指定月份才解压；不并入当前 Data，不执行迁移、排期或完成命令。重复 archiveId＋同 hash 去重；同月份不同来源并存或提示，不能静默覆盖；同 ID 内容冲突明确拒绝。页面清楚标为“历史归档／只读”。

归档步骤需要新的具名生命周期命令与依赖检查。现有普通事务的 facts/history/instances 不可删规则继续生效，不能在普通 Save 内偷偷过滤旧数组；正式归档是将确定记录转入已验证档案的专门操作，保留 archiveId、清理回执和摘要。IDB 表升级仍不自动归档或处理个人数据。

### 13.2 哪些清理，哪些继续保留

| 活动区长期保留 | 可归档的封存记录 | 不按日历直接删除 |
| --- | --- | --- |
| 原卡、条目、牌堆、决策、模板、现行生成规则及必要版本来源 | 无活动引用的已确认事实、已封存计划及批注；旧日记／感想；已封存操作历史 | 未完成／跨月行动、未来排期、当前手牌、仍在使用的答案或合成谱系 |
| 活动对象需要的依赖、生成幂等记账摘要、消费与归档索引 | 到期副本、无活动依赖的旧来源版本与历史 | 当前对象所引用的旧 ID／版本，以及重复操作防护所需信息 |

“一个月的数据”不能简单按 at 的月份筛选。例如 10 月拿出、11 月才完成的行动要连同依赖继续留在活动区；跨月事实作为一个完整来源存档，月份索引可以关联其两侧日期，不能拆成两个完成事实。打包按封存记录的关系闭包，不删掉仍被活跃内容使用的部分，预览须解释延期归档原因。

归档将减少“常驻历史”而非保证活动区永远固定一个月：大量未完成内容或用户一直未导出时仍会增长。原库也不会因归档缩小；仍须有容量提示和可恢复拒绝边界，不能声称分月后无需门槛。

### 13.3 必须明确的合同变化与验证

- **编辑范围**：若选择归档只读，已移出月份不能按原路径直接修改旧日记／排期；需要决定“完全只读”还是“允许在当前工作区新增补记／补充说明并引用归档，原包不修改”。后者不等于恢复归档为可写；现有追加批注和自由补写规则要明确适配。
- **完整恢复**：当前 JSON 主备份将只包含活动区及归档索引；完整历史恢复需要“当前主备份＋归档 ZIP”。须准确标示缺失包和需要的 archiveId／hash，不能继续宣传单个主 JSON 包含所有历史。旧 v1—v4 完整备份的精确恢复继续支持。
- **可靠副本**：本机压缩 Blob 可以保留用于只读查看而不常驻内存，但它与活动区同属浏览器存储，清浏览器仍会丢失；因此不能用本机副本替代已验证的外部归档包。用户可以选择不保留本机包，之后查看时重新选入。
- **安全边界**：逐包处理，限制压缩文件大小、解压实际字节、条目数及嵌套深度；只认白名单 JSON，不执行包内脚本、不接受路径逸出或嵌套 ZIP。解压 byte budget 按实际输出限制，不能只相信 ZIP 声明的大小。包损坏、缺依赖、版本未知和部分失败不触发活动区清理。
- **主库缩减及兼容**：需要专门归档事务、跨月引用处理、历史查询端口与旧数据批次预览。没有这些不能先做“清空上个月”按钮。新归档路线会增加 B 线工作并影响 A 的日记只读状态，应在 P0 前统一，不能让 A 按集中可编辑模型写完后再返工。

新增 31 天规模探针：相同频率模型紧凑 JSON **1.82 MiB**（124 随记、186 事实、806 历史及回执），合法 v4 控制组完整校验约 **345 ms**。一年控制组为 3.49 秒，三年为 13.89 秒。它支持“缩小工作集”的方向，但未包含跨月依赖闭包、ZIP 解压、归档索引、只读 UI 或清理恢复，不能据此冻结归档包大小／内存预算或称归档已验收。

本轮保留第 12 节卡牌、日记身份、文件故障候选；容量、主备份范围、旧月份编辑及新归档生命周期暂不冻结。下一步先确定月度路线及归档后编辑范围，再补共同格式、跨月反例、实际 ZIP／加载释放／精确恢复探针，调整并行任务。无个人数据被清理，无生产格式或门槛被修改。

### 14.2 调用与失败合同

- 所有业务提交携带 `contractVersion:v06-p0-1`、commandId 与 `{epoch,revision}`。对象使用 ID＋version；预览、选择、导入和清理凭据由端口发出，调用方不能自填结果或伪造“verified:true”。正式 Host 仍须重验能力与源指纹，按同 commandId 重放原回执。取消预览只销毁会话能力。
- 读取统一返回 live token＋不可变展示快照。答案／资源无可执行 Content，行动／成品才有行动字段；参考点与贴附位置使用互斥分支，不再以一组可随意组合的 nullable 字段表达。旧 Instance、Fact、Annotation 与历史原结构不变。
- 日记区分 `access:live, editable:true` 与 `access:archive, editable:false`。归档视图无当前提交 token、无修改端口，不在归档页补记或恢复成可写。是否允许另从活动区补记已归档日期，须在 B3/B4 的正式日期规则中核对，不通过“可编辑归档”解决。
- 随记创建只接受 date／zone／text，编辑增加 id／expectedVersion；原时间由正式写入端产生，调用者不可提交 recordedAt。旧正文单独按块 ID／version 修改，不拆句子、不伪造时间。
- 业务、文件两类结果分开：业务成功并不代表文件 synced。文件端口通过 bindingId／connectionVersion／epoch 隔离旧任务，隐藏句柄；保留最近成功输出、待写源版本、写入意图和 reconcile-required 状态。主数据不得因文件失败回滚，用户文件外部变更不导回工作区。归档后不得以不完整活动数据覆盖已经生成的旧日文本；B9/B11 必须联合验证源覆盖和队列排空。
- 维护日志只记录 CardGrid 操作与打开清单网址的请求和结果，不声称观察了外部页面。维护事件、文件缓存及授权不进入业务主备份。

### 14.3 月度归档与容量端口

归档链固定为 **预览 → 导出 → 外部重读校验 → 清理预览 → 明确提交**。清理提交需要导出预览 ID、验证 capability ID、清理预览 ID 和 `removalConfirmed:true`；实际清理资格仍由正式 Host 检查，接口字段本身不提供删除授权。未导出、文件损坏、缺依赖、旧 token、工作区替换、事务失败都不移除活动记录。

readArchivableMonths 返回绑定当前 token 的月份、可归档／需保留记录数及估算字节，供应用内月度提醒；该查询不解压历史包，也不写数据。正式提醒只在应用打开时运行，未处理月份继续显示，不新增后台定时器或自动删除。

预留 ZIP 为 manifest.json＋records.json；manifest 记录 workspaceId／archiveId、月份／时区、源版本、覆盖日期、集合计数与 SHA-256。跨午夜可以覆盖两个月的日期，不能把事实拆成两条；records 保留独立解释需要的版本快照、原事实、批注、旧正文及历史。固定白名单路径，未知版本／字段、重复路径、引用缺失和 hash 不符拒绝。

多个包逐个调用 importArchive，结果分别 added／duplicate；同 archiveId 内容冲突拒绝。正式适配器只保存压缩包和小索引，按月加载只读 ArchiveView，切换时释放解码对象；包内对象不并入活动 Data。小索引进入主备份，压缩 Blob／句柄留在适配器私有存储。Backup5 明示 `coverage:active-plus-archives` 和 requiredArchives；缺包时当前数据仍可读，但不得报告完整历史恢复。

CapacityPolicy 独立提供活动主备份、输入、压缩包、实际解压字节、包条目数及同时解码月份的预算，状态为 provisional／validated。输入预算必须覆盖所有获准主备份；字节等于门槛允许、下一字节拒绝，使用 UTF-8 实际字节。**P0 不给未经 ZIP／闭包／正式 Host 验证的数值盖章**，也未修改当前生产 5 MiB。fixture 的 KiB 数值仅用于边界反例，不是产品门槛；C0 的 32／64 MiB 仍是集中路线历史提案。

新增 M01—M12 月度字面向量覆盖未导出、外部重读、跨月保留、重复／冲突、缺依赖、旧预览、只读、缺包、解压超限、释放旧月及 epoch 替换。它们与 C01—C32 都是后续行为验收输入，不能因 P0 测试通过就标为归档／合成已实现。

### 14.4 冻结与后续门槛

本轮公开接口的精确版本为 v06-p0-1（draft），先供 A/B 对同一 fixture 核对。F1—F3、归档后活动区补记、跨月依赖闭包及容量数值仍有候选内容；本轮没有把它们改记为用户已确认。双方核对和必要探针完成后更新冻结状态，差异先改合同／fixture 再改调用。正式写入须同时具备严格全包校验、执行、拒绝路径、回执、真实 IDB 故障和精确恢复证据；不得仅把端口标记改成 formal。
