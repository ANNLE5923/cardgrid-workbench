## 当前正式路径

```text
main.tsx → app/App + app/use-workspace-app（应用壳、权威快照/token adopt）
  → DayBoard（日期/时区/来源视图、唯一活动排期所有者）
    → TimeDial / HandFan（几何、显示、操作意图）
    → usePlacementSession（串行合并预览、代次失效、完整命令重试）
  → workspace/client（冻结2C-host-1）
    → workspace/commands / daily/model（能力与领域命令）
    → workspace/store.atomic（IndexedDB事务、回执、跨窗口通知）
```

读侧由workspace-client.readDay调用action-projection；projection-adapter把权威片段转换为盘面，不另造占用/时间规则。实际与事实复用action-flow组件，按钮排期也复用同一会话控制器。固定重预览先取得新解锁，再释放旧预览。24:00在控制器转为次日00:00，不向Host提交1440。

正式源代码不导入原型、docs合同或测试fixture。G3本轮仅修改界面、会话和几何适配，九个领域/Host/存储/格式核心文件与冻结指纹一致；见[G3验收记录](../归档/阶段0-3/测试记录/G3-2026-10-02-有界修复与最终验收.md)。

## 1. 技术栈与运行环境

- **前端**：React 19、TypeScript、Vite 7；入口为 `src/main.tsx`。
- **页面状态**：React `useState`/`useRef`；仓库没有 Zustand、Redux 或服务端状态库。
- **领域逻辑**：`src/planner.ts` 中的命令、约束和快照校验；`src/domain.ts` 中的配置与导入包校验。
- **存储**：浏览器 IndexedDB，数据库 `cardgrid-workspace`，对象仓库 `workspace` 和 `recovery`；BroadcastChannel 只通知其他窗口，不做云同步。
- **构建与测试**：`npm run build` 运行 TypeScript 检查和 Vite 构建；`npm test` 使用 Node 内置测试运行器。生产构建注册 Service Worker 缓存应用文件。

## 2. 系统结构

```text
用户
  ↓
main.tsx（导航、配置、Inbox、数据管理、提交协调）
  ├─ today.tsx（当日展示与操作）
  └─ schedule.tsx（日型与当天安排）
       ↓ 复制 Data 后调用领域命令
planner.ts（Planner 快照、校验、历史记录）
  ↓ 通过 main.tsx 的 onSave / persist
store.ts（校验、revision 比对、IndexedDB 事务、恢复点）
  ↓
本机浏览器 IndexedDB
```

没有单独的 API 服务器。`domain.ts` 定义顶层 `Data`、旧配置和导入格式；`planner-migration.ts` 负责旧数据转换与一次性配置导入。页面不直接写 IndexedDB，但 `main.tsx` 同时承担页面展示、导入流程和提交协调。

## 3. 真实文件与责任

| 文件 | 主要责任 | 当前依赖方向 |
| --- | --- | --- |
| `src/main.tsx` | 应用壳、配置工坊、Inbox、备份导入、保存协调、启动 Bootstrap | 调用 Today/Schedule、domain、planner、store |
| `src/today.tsx` | 当天展示、Top3、例行操作、快速捕获 | 调用 planner 命令，经 `onSave` 返回提交结果 |
| `src/schedule.tsx` | 模板草稿、当天时段、冲突反馈、拖拽 | 调用 planner 命令，经 `onSave` 返回提交结果 |
| `src/planner.ts` | Task/Rule/Day/Capture 等领域类型、命令、校验、历史 | 不依赖 React 或 IndexedDB |
| `src/domain.ts` | Config/Data/Envelope、校验、导入包与恢复格式 | 组合 Planner，调用迁移逻辑 |
| `src/planner-migration.ts` | 旧字段映射与旧配置的一次性导入 | 依赖 domain 类型与 planner |
| `src/store.ts` | IndexedDB 读写、revision 冲突、恢复点、跨窗口通知 | 提交前调用 domain 校验 |
| `src/app/style.css`、`scripts/vite.config.ts` | 界面样式、构建与离线资源 | 不承担业务规则 |

`domain.ts` 在运行时调用 `planner-migration.ts`；迁移文件对 `Data` 只作类型导入，因此这里没有运行时循环依赖。新增逻辑仍需保持迁移与常规保存的责任边界。

## 4. 核心数据流

**快速捕获**：Today 输入 → 复制当前 `Data` → `createCapture(planner, text)` 写入 `Capture` 与 `History` → `onSave` → `store.commit` 校验并比较修订号 → IndexedDB → React 用新 `Envelope` 重渲染。只有提交成功才清空输入。

**改当天日程**：Schedule 编辑本地草稿 → 保存按钮 → `putBlock`/`moveBlock`/`cancelBlock`/`replaceTemplate` 检查日期及冲突并更新 `Day` → `store.commit`。冲突或保存失败时不提交，草稿仍在页面。

**每日初始化**：启动 `store.load` → `importDefinitions`（只在 `legacyImported=false` 时导入旧定义）→ `bootstrap` 确保今日 `Day`、生成适用例行、标记过去错过项 → 若发生变化再 `commit`。重复打开同一天不会重复生成同一规则实例。

**备份恢复**：读取文件 → `parseImport`/`applyImport` 校验并生成预览 → 下载操作前备份 → `persist` → `store.commit`。配置包只修改 `Config`，完整备份包含整个 `Data`。

## 5. 核心领域模型

```text
Envelope { schemaVersion: 3, revision, data }
└─ Data
   ├─ config（偏好/分类/旧卡片定义/旧日程模板）
   ├─ planner（当前 Today、Inbox、Schedule 的主要业务事实）
   │  ├─ Template → Day 快照 → Block
   │  ├─ Rule → Occurrence → Task
   │  ├─ Capture → 可选择转换为 Task
   │  ├─ Task ↔ Day.top3（按 ID 引用）
   │  ├─ Ref / Goal（可存储关联，当前页面管理有限）
   │  └─ History（有意义的变更记录）
   └─ 旧版字段及 legacyArchives（迁移/兼容保留）
```

`Planner` 保存当前快照，同时追加有意义的 `History`；它不是从事件日志重放得到状态的 Event Sourcing。`Template` 是长期定义，`Day` 是某日快照；`Capture` 不是 `Task`；`Occurrence` 表示某规则某日的实例，补做另建 Task 并指向原实例。`Config.Card` 与 `Planner.Task` 名称接近、语义不同，不能在讨论中混用。

## 6. 状态管理

| 类别 | 当前示例 | 放置位置 |
| --- | --- | --- |
| UI 临时状态 | 当前标签、选中日期、弹窗、保存中、草稿 | React 组件 `useState`/`useRef` |
| 业务状态 | Task 状态、Capture 状态、Day 例外、Rule 状态 | `Data.planner`；经领域命令修改 |
| 持久化状态 | `Envelope`、恢复点、配置包导入结果 | IndexedDB；由 `store.ts` 提交 |
| 派生视图 | 当天任务、可选 Top3、未处理 Inbox、排序后的时段 | 页面从 `Planner` 过滤/排序，不另存一份列表 |

## 7. 已验证的架构约束

- 业务变更先在克隆的 `Data` 上执行领域命令，再由 `store.commit` 统一校验与事务提交。
- `revision` 防止另一个窗口的旧快照覆盖新数据；BroadcastChannel 负责提醒重新载入。
- 日期例外在 `Day` 中，模板更新不改写既有 Day；过去日期的日程写命令会拒绝。
- Inbox 捕获不直接生成 Task；历史中保留有意义的状态变化。
- 导入前校验格式；外部完整备份比本机单个恢复点更适合作为长期数据保护。

## 8. 当前架构问题（待讨论，不在本文直接改代码）

| 问题 | 证据与影响 | 现在是否处理 |
| --- | --- | --- |
| 双层定义与一次性导入 | `Data.config` 和 `Planner` 同时保存卡片/日程概念；`importDefinitions` 在 `legacyImported=true` 后跳过，后续配置修改不自动进入 Planner，容易形成两个事实来源。 | 先在 Q001 定义所有权和迁移边界，再考虑改造。 |
| “转 Card”到“今天做”断链 | Inbox 解析出的 `Task.date=''`；Today 只展示 `date===today`，页面没有对普通 Task 的排期入口。 | 作为核心使用路径优先设计，见 Q002。 |
| 例行规则可存但难配置 | Planner 有 `Rule` 和生命周期命令，但 UI 只提供当天操作；新规则管理缺入口。 | 先核对真实用户需要的最小规则编辑，再设计入口。 |
| `main.tsx` 责任集中 | 单文件同时处理导航、配置表单、导入、备份、保存和 Inbox；未来改动更易耦合。 | 暂不为“目录漂亮”做大重构；伴随实际功能边界调整。 |
| 旧文案与现状不一致 | 配置工坊仍显示“P2 再应用到日期”和数据页“日程操作将在后续阶段”，但 Schedule 已实现。 | 文案小修可独立完成，见 Q004。 |

## 9. AI Talk 新愿景与 P1A 模型对照（设计输入，不是实施方案）

| 未来概念 | 当前可继承的基础 | 明确缺口/不可混同之处 |
| --- | --- | --- |
| 候选卡池与抽取 | `Config.Card` 有标题、类别、分钟、启用状态；Planner 有 `Task` | 没有抽取规则、权重/过滤、抽取实例或重抽语义；卡片定义不等于一次行动。 |
| 手牌 | `Capture` 表示未整理想法，`Task` 表示待办/状态 | 两者都不是“已选但未排期的可持有牌”；需要定义实例、顺序与回收语义。 |
| 今天的时间盘 | `Template`、`Day`、`Block` 有固定/弹性、冲突检测和日期快照 | 当前只呈列表/时段，未建 24 小时双环、实时指针、旋转与可用时段计算。 |
| 打出与回收 | `putBlock`/`moveBlock` 可操作当天 Block | 没有“手牌 ↔ 计划块”的同一实例身份与可逆迁移；现有命令对过去日期禁止修改。 |
| 完成事实 | `Task.status` 和 `History` 记录完成/恢复等变化 | 现有 done 可恢复为 planned；Block 没有实际起止或完成状态；History 不是不可改的事实表。 |
| 批注和领域数据 | `History` 可保留操作前后状态 | 没有面向用户的追加批注、饮食/消费载荷和聚合规则。 |

**最小设计问题**：卡牌定义、一次抽取/手牌实例、一个可改的计划块、一次由用户确认的实际发生，是否必须是四种不同身份？先用“抽一张行动卡 → 进手牌 → 打出 → 移动/撤回 → 确认”做原型和迁移评估，再决定字段与 P1B 范围。不要直接把 `Task.status='done'` 当成不可变事实。

**已定产品约束与技术边界**：用户确认完成后，原事实内容和实际时间在应用内永久不可修改；只允许追加带时间戳的批注。实现时不能继续把 `Task.status=done` 当作可恢复的事实，需要独立区分计划与确认记录，并定义导入、恢复、录错及旧 `done` 数据的处理。浏览器 IndexedDB 和用户持有的旧备份无法提供密码学意义的“不可篡改”；对外只能准确说明应用内规则，不能宣称物理上绝无改写可能。
