> 共同决策记录。这里的“已确定”来自现有产品定位或代码约束；AI Talk 讨论稿中的新方向单列，不自动视为实现规格。讨论后更新结论、原因、日期和受影响文件。基于 2026-09-24 的代码快照及用户转交的 AI Talk 整理稿。

## 已确定决策

### D001｜Today 作为默认入口

- **决定**：Today 是打开工作台后的默认视角，其它页面辅助当天行动。
- **原因**：用户首先需要理解“今天是什么样的”；见[项目总览](./00-项目总览.md)。
- **代码证据**：`src/main.tsx` 的初始 `tab='agenda'`，侧栏第一个入口是 Today。
- **状态**：现有 P1A 决策。改变默认入口需先重新讨论产品目标。

### D002｜本地优先、用户掌握备份

- **决定**：无需账号；工作区默认保存在当前浏览器，提供完整备份、导入预览和恢复点。
- **原因**：降低开始使用的门槛，让个人数据与工作方式由用户控制。
- **代码证据**：`src/store.ts` 的 IndexedDB/恢复点、`src/main.tsx` 的导出和导入入口。
- **状态**：现有 P1A 决策。不能把“本地优先”误写成“数据绝不会丢失”；用户仍需主动保留外部备份。

### D003｜Capture 先于 Task

- **决定**：快速捕获只创建 `Capture`；转 Card 是显式动作，不自动进入 Today/Top3。
- **原因**：想法出现时不要求立即决定日期或优先级。
- **代码证据**：`src/planner.ts` 的 `createCapture`、`resolveCapture`，`src/main.tsx` 的 Inbox 操作。
- **状态**：现有 P1A 决策。若未来增加自动整理，先重新讨论这条边界。

### D004｜日型模板与当天快照分离

- **决定**：长期 `Template` 与具体 `Day` 分开；当天例外不反向污染模板。
- **原因**：计划要可复用，现实变化也要能留下痕迹。
- **代码证据**：`src/planner.ts` 的 `ensureDay`、`putBlock`、`cancelBlock`、`replaceTemplate`、`saveTemplate`。
- **状态**：现有 P1A 决策。

### D005｜现有 P1A：保存当前快照并追加有意义的历史

- **决定**：当前状态保存在 Planner 数组中；重要变化追加 `History`。不采用从事件日志重放全部状态的 Event Sourcing。
- **原因**：日常读取简单，同时保留计划调整与完成的证据。
- **代码证据**：`src/planner.ts` 文件首注释与 `record`/各领域命令。
- **状态**：现有 P1A 决策。

### D006｜过去例行不改写，补做另建任务

- **决定**：例行事项每个适用日期有自己的实例；错过/跳过保留原记录，补做建立新 Task。
- **原因**：避免将昨天没做的事伪装成今天自动完成或自动滚动。
- **代码证据**：`bootstrap`、`changeStatus`、`makeup`；领域测试见 `tests/routine-lifecycle.test.ts`。
- **状态**：现有 P1A 决策。

### D007｜Minimum Day 手动切换，不删原计划

- **决定**：用户主动切换 `Day.minimum`；原 blocks、tasks、Top3 保留。
- **原因**：最低运行模式改变当天关注点，不应擦除原计划。
- **代码证据**：`setTodayMode` 与 `tests/minimum-day.test.ts`。
- **状态**：现有 P1A 决策。

### D008｜确认完成后原事实永久不可修改

- **决定日期**：2026-09-24，用户在本次对话中明确选择“已定案：完成后永久不可修改”。
- **决定**：只有用户主动确认才能创建完成事实；确认后原事实的内容与实际时间在应用内永久不可修改，也不能撤回成未完成。后续理解只能通过带独立时间戳的追加批注表达，不能覆盖原事实。
- **原因**：区分可逆的计划与真实发生的记录，避免事后重写生活史；时间流逝本身不生成事实。
- **实施状态**：**已定案但未实现**。现有 `changeStatus` 支持 done→planned；`Block` 不存实际时间，`History` 不是独立事实层。实现前必须解决 Q007 的事实结构、录错说明、导入恢复和迁移语义。
- **边界说明**：“不可修改”指应用内产品规则。本地 IndexedDB 和旧备份无法保证密码学或物理层面的不可篡改，对外不能作此承诺。
- **工作区生命周期**：见 D012、D013。不可改写约束作用于当前工作区内的事实记录；完整备份恢复或清空会替换/清除当前工作区数据，之后的事实不会自动并入新状态。

### D011｜完成确认时填写实际起止时间

- **决定日期**：2026-09-24，用户在阶段零复盘讨论中选择“填写实际区间：确认时要求用户填写实际开始和结束；默认填写计划时间，用户自主调整”。
- **决定**：确认完成必须提交实际开始与实际结束时间。存在计划区间时，确认界面先以计划开始/结束填入实际时间，用户可在确认前调整；这只是待确认的表单初值，不代表实际已经发生。实际区间经用户确认后锁定，不得再编辑或覆盖。确认时间独立记录为系统收到确认的时间。
- **未覆盖的边界**：没有计划区间时，用户需自行填写实际起止；跨午夜区间如何填写、显示和归属日期，留待 Q009 / 1A 时间合同明确。填写区间校验及无效输入提示也在 1A 合同确定。
- **原因**：用户希望记录实际发生区间，同时保留完成操作的明确确认；用计划区间作可调整的初值减少重复输入，不把计划值自动当作事实。
- **实施状态**：产品交互规则已决定，尚未实现；继续遵循 D008 的应用内永久锁定与追加批注原则。

### D012｜完整备份恢复采用整工作区替换

- **决定日期**：2026-09-24，用户明确选择“让恢复结果完全等于备份”。
- **决定**：恢复完整备份后，当前工作区整体等于所选备份的 `Data`；不把当前工作区中、备份生成后新增的计划、事实、批注或其它数据自动合并进来。恢复操作前仍按现有交互下载当前完整备份，供用户自行保留或再次恢复。
- **与 D008 的关系**：事实在工作区内不可编辑、覆盖或撤回；但工作区快照恢复会替换其集合，较新事实若不在所选备份中，将不再属于恢复后的当前工作区。因此产品不承诺事实跨快照回滚永久保留。该规则尊重用户明确选择的精确恢复语义。
- **原因**：用户期待“恢复”得到一个可预测且与备份完全一致的工作区；自动并入当前事实会使恢复结果不再等于备份，并引入去重、冲突及旧版本兼容规则。
- **实施状态**：产品恢复语义已定；恢复前下载当前备份为现有行为，阶段 1/2 仍须实现恢复测试，验证恢复后 Data 与所选备份逐字段相等。

### D013｜清空后不在新工作区保留旧事实

- **决定日期**：2026-09-24，用户明确选择清空后工作区彻底空白，事实仅存在于用户自行保留的备份中。
- **决定**：清空操作完成后，当前工作区为全新空状态；不在应用中新建旧事实归档或把旧事实带入新工作区。清空前下载的完整备份是用户自行找回旧状态的来源，应用不保证在清空后的工作区继续保存副本。
- **原因**：清空应确实让用户从空白状态重新开始，避免旧记录悄悄残留或被恢复进新工作区。
- **实施状态**：产品语义已决定；阶段 1/2 需验证确认步骤先下载完整备份、清空后业务数据和本机恢复点均为空，并可通过用户保留的外部备份自行恢复。

### D014｜手牌选取、磁吸落点与卡牌时长

> 本节记录最初决定；容器、空闲限制、双候选与松手提交规则已由 D018 覆盖，以 D018 为准。

- **决定日期**：2026-09-24，用户在阶段零后的产品细节讨论中明确交互规则。
- **决定**：手牌以固定容器中的叠牌堆呈现；点击牌堆后在屏幕下半部围绕一个屏幕外共用支点按角度向两侧展开。卡牌露出部分内容；点击卡牌只将其抬高并置顶供查看，其余卡牌保持原位，不代表打出。
- **打出条件与磁吸**：打出必须落在当前指向的、属于用户自己的空闲时间区间。拖动卡牌时，其上边缘变形成与卡牌颜色一致的环形线段作为区间预览；落点按 5 分钟单位左右微调。若同一时刻对应的两个十二小时区间都空闲，则同时显示两处对应轮廓提示。选择有效落点并释放后才占用区间；无效区间不得打出。
- **区间长度**：由卡牌预设时间决定，以 5 分钟为一个单位；例如 15 分钟占 3 个单位，25 分钟占 5 个单位。
- **实施状态**：产品交互规则已确定，尚未实现；仍需在交互原型/实现规格中明确卡牌颜色线段的准确含义、有效区间判定反馈，以及牌堆数量变化时扇形展开与可点击区域的适配。

### D015｜实际区间重叠时再次确认后允许记录

> D018 已把明确确认后允许重叠扩展到卡牌计划及解锁后的固定安排；下文“计划排期继续要求完整可用区间”为历史描述。

- **决定日期**：2026-09-24，用户在 1A 合同设计中选择“提示重叠，用户再次确认后记录实际区间”。
- **决定**：填写的实际区间与已有计划（包括固定安排）或完成事实相交时，列出重叠对象和区间；用户再次明确确认后仍可创建本次完成事实。其他计划、固定安排和事实不自动移动、截短、撤回或改写。计划排期继续要求完整可用区间。
- **原因**：实际发生可能偏离或重叠计划；记录真实发生不应被排期约束强行改写。
- **实施状态**：产品规则已确定，尚未实现。二次确认凭据需绑定本次草稿与工作区修订，数据或区间变化后重新提示；具体合同见 [1A 草案](../归档/阶段0-3/产品设计/06-1A领域时间与迁移合同.md)。

### D016｜允许提前确认未来结束时间

- **决定日期**：2026-09-24，用户在 1C 选择“允许提前确认未来结束时间”。
- **决定**：实际填写按分钟，不强制 5 分钟取整；不以结束时间晚于确认时刻为拒绝条件。仍检查起止有效、开始早于结束，并按 D015 处理重叠。confirmedAt 保留真实操作时刻，不能伪装成实际结束时刻。
- **与 D008 的关系**：提前确认也立即创建锁定记录，没有等待结束后的二次自动完成或撤回窗口。确认前明确标示“结束时间尚未到达，确认后不可修改”；历史可由 confirmedAt 与实际结束对比显示“提前确认”，不声称系统验证了未来行为。
- **实施状态**：已决定，待实现；取代 1A/P03 的“禁止未来结束”建议。时间流逝本身仍不生成事实。

### D017｜日终自动显示红色空时间，实际区间占时

- **决定日期**：2026-09-24，用户选择“每天结束自动显示，红色随记录重新计算”，以及“实际区间占时，原计划仅作对照”。
- **决定**：以工作区所选时区的当地日期结束为日终；到下一当地零点，该日空闲范围自动显示红色，之后补记/调整时重新计算。应用关闭时不必后台运行，下次查看已结束日期时直接计算。红色是视图占位，不生成事实、不储存冻结区间，也不触发自动 PrepareDay。
- **占用口径**：固定安排、未确认活动计划、已确认记录的实际区间参与并集；确认后原计划仅为对照轮廓，不重复占时。红色等于日范围减占用并集；重叠实际不重复扣减。提前确认的区间也按 D016 进入占用计算。
- **实施状态**：已决定，待实现；与 D012/D013 的只读加载一致，不需要持久化“已结束”标记。细节见 [1C 合同](../归档/阶段0-3/产品设计/07-1C合同收敛与原型接口.md)。

### Q001｜旧 Config 与 Planner 谁是未来的事实来源？【优先】

### Q007｜怎样落实已定案的事实锁定规则？【架构阻断】
