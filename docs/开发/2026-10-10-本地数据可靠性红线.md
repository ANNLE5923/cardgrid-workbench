# 本地数据可靠性红线（v0.6.5 收口）

本文记录 CardGrid 本地优先数据层**不可破坏的不变量**。任何涉及存储、读取、迁移、恢复、指纹、归档、导出的改动，都必须先满足这些红线；复杂架构变更按此审查，普通功能不必逐条套用。

代码坐标以 v0.6.5 为准：`app/src/workspace/`（store / format / v06-host / safe-recovery / v5-format / v5-recovery-restore）、`app/src/app/RootApp.tsx`、`app/src/app/V06SafeOpen.tsx`。

## 1. 三条相互独立的版本轴

| 轴 | 载体 | 当前值 | 决定什么 |
| --- | --- | --- | --- |
| IndexedDB 版本 | `indexedDB.open(name, 5)` | 5 | 对象仓库/索引结构，仅在 `onupgradeneeded` 里建改仓库 |
| 信封版本 | 信封 `schemaVersion` | 4 | 信封外壳形状 |
| 业务数据格式 | 信封 `dataFormat` | action-v2 / v3 / v4 / v5 | 业务 JSON 的真实结构 |

**IDB 版本不变，不代表业务数据格式没有变化。** Data v5 的信封是 `schemaVersion:4 + dataFormat:'action-v5'`：IDB 仍是第 5 版，但业务格式已经换代。判断数据格式必须看 `dataFormat`，不能只看 IDB 版本。

## 2. 打开数据库绝不迁移业务 JSON

- IDB `onupgradeneeded` 只允许创建/调整对象仓库与索引（如 `pre-p1a` 这类结构迁移备份），**禁止**在其中重写业务 `data`。
- 业务格式升级只能走显式生命周期命令 `CommitMigration`：先 `prepareBackup`（下载完整备份）→ `previewMigrationV5`（预览）→ 用户勾选确认 → 单事务提交。任何“打开时静默升级”都不允许。
- 旧格式（v2/v3/v4）打开时是只读/引导升级，不会被隐式写成新格式。

## 3. 读取器与只读安全降级必须成对存在

- 正常读取链：`inspectEnvelope/inspectSnapshot` 识别 action-v2/v3/v4；action-v5 走独立严格链 `isV5 → validateV5Envelope → validateDataV5 → validateV5Fingerprints`（`v06-host.ts` 的 `snapshot()`）。
- 只读安全链：`host.readSafeOpen()` + `parseSafeRecovery()`。它**不经过任何校验器、不需要 live token**，只用 readonly 事务直读 `workspace/current` 与 `recovery/*`，尽力解析、永不抛业务错误、永不写入。
- **新增一个 `dataFormat` 时必须同时做到三件事**：
  1. 在正常读取/校验链登记；
  2. 只读安全面无需通过新校验就能浏览与导出该格式（否则坏数据在进入展示层前就被拒绝，安全面也拿不到原文）；
  3. 保留上一代读取器与对应夹具测试。
- 当前数据认证失败时，`RootApp` 挂 `V06SafeOpen`（旧版 v4 为 `SafeRecoveryView`）：可浏览集合、导出当前原文、导出 `recovery/*` 恢复点原文、重试正常打开；**不含**任何编辑、出牌、确认或写回式恢复。

## 4. 删除旧读取器的前置条件

只有同时满足才能删除某一代读取器/夹具：

1. 发布通道确认已不存在该格式的本地库；
2. 显式迁移预览与提交对该格式仍有覆盖测试（schema1 信封、legacy backup、action-v2/v3/v4/v5 current 的夹具保留在 `app/tests/`）；
3. 只读安全面对该格式的导出往返测试通过。

## 5. 指纹基于规范化 JSON，而非原始字节

- IndexedDB 存的是结构化克隆，**没有原始字节**，因此内容指纹用 `canonicalJson(...)`（规范化 JSON）计算，不能用字符串哈希。
- 恢复预检（`previewRecoveryPoint`/`guardedV5Target`）与提交（`RestoreRecoveryPoint`）都必须比对恢复点原文的**内容指纹**；确认动作还要绑定预检时的工作区 token 与内容版本，数据变化后要求重新确认，不能只按恢复点名称恢复。

## 6. 读写事务纪律

- 所有读走 readonly 事务：`store.read()`、`store.readRecovery()`、文本/归档只读方法。
- 所有业务写在**单个** readwrite 事务内提交；事务内任一校验失败即整体 abort，不留半截数据。
- `recovery/previous` 与新 `current` 在**同一事务**轮转：先把旧 current 写入 `recovery/previous`，再写新 current，保证任意时刻都至少有一份上一份的好数据。
- 丢失回复重试：先识别已持久化的命令收据/生命周期回执，再判断恢复点是否变化，避免“其实已成功却被重试拒绝”。

## 7. 派生物缺失只诊断，不阻塞活动区

- `text-output`（导出文件状态）与 `monthly-archive` 索引/ ZIP 都是**可重建的派生物**，不是唯一真相源。
- 唯一真相源是活动工作区 JSON（IDB `workspace/current`）。派生物缺失或损坏时只记录诊断，不得阻止活动区打开与使用。

## 8. 兜底也要验收

- 每新增一条兜底/恢复路径，至少配一个 `app/tests/modules/` 自动测试（判断与命令正确）和一次带数据的浏览器验收（按钮、刷新、重试、下载、零写入接线正确）。
- 安全面验收要点：坏数据能进安全面、打开零写入、无任何编辑入口、可导出当前与恢复点原文、未修复时重试仍停留、修复后重试回到工作台。

## 9. 暂未做（边界）

- 安全面的**写回式一键恢复/清空损坏工作区**在 v0.6.5 不提供。它需要以恢复点原文指纹为凭据、不依赖 live token 的生命周期动作，且要有开源先例（思源 repair、Excalidraw restore）与事务/回执测试后再做。当前版本先用“只读浏览 + 导出原文 + previous 留存”保证数据不丢、可读。
