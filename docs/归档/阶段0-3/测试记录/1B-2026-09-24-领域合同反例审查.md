## 一、审查方法

按用户真实操作路径走查合同，重点覆盖 05 计划指定的 8 个领域：重复完成、并发完成、错录、旧备份恢复、清空、跨午夜、固定块误拖、取消后重复打出。

每个反例记录：场景描述、触发的合同规则、合同预期、验证方式（静态推演/需运行时验证）、严重程度、修订建议。

严重程度：
- **阻断**：合同内部矛盾或关键遗漏，G1 放行前必须解决
- **高**：边界情况未覆盖，可能导致数据不一致或用户操作卡死
- **中**：交互细节未明确，不影响核心数据安全但影响可用性
- **低**：文案或展示问题

## 二、反例清单

### A. 重复完成

#### R-A01｜确认完成后刷新页面，UI 未隐藏操作入口

- **场景**：用户在窗口 A 确认实例 X 完成（产生 Fact），不刷新页面。然后刷新页面。刷新后 UI 重新从 Data 渲染，实例 X 已有 Fact。
- **合同规则**：第 4 节"已有 Fact | 再次完成、移动、回收、改名/时间 | 拒绝"；第 3 节"确认事实后实例不可再打出、回收、编辑或撤下"。
- **预期**：刷新后实例 X 不在手牌中、不在可安排列表中；Today 页面显示为已确认事实，无"完成"按钮、无"撤回"按钮、无拖动手柄。
- **问题**：合同只规定了领域层拒绝，没有规定 UI 层必须隐藏哪些入口。如果 UI 仍显示"完成"按钮，用户点击后领域层返回 ALREADY_CONFIRMED，但用户看到的是"操作失败"而不是"已经完成了"。
- **验证方式**：需运行时验证（阶段 2 UI 实现后）。
- **严重程度**：中
- **修订建议**：在 1C 合同中补充 UI 状态映射：已有 Fact 的实例在所有页面中只读展示，操作入口不渲染；领域返回 ALREADY_CONFIRMED 时 UI 显示"已完成"而非错误提示。

#### R-A02｜同一实例先打出计划，再从手牌直接确认，产生两个路径

- **场景**：用户接受实例 X 进入手牌。打出 X 到 09:00-09:30（产生 Plan A，X 移出手牌）。然后用户撤回 Plan A（X 回手牌）。然后用户不打出，直接从手牌"补记实际区间"确认 X 完成（产生 Fact）。
- **合同规则**：第 4 节"手牌或活动计划 | 确认实际 | 新 Fact；活动计划封存为 confirmed；退出手牌"。
- **预期**：从手牌直接确认时，没有活动计划需要封存，只产生 Fact，X 退出手牌。Plan A 保持 retracted 状态。
- **问题**：合同说"活动计划封存为 confirmed"，但从手牌直接确认时没有活动计划。这个分支是否允许？第 3 节流程图有"Hand → 直接补记实际区间 → Fact"，所以允许。但命令表中 ConfirmActual 的输入是"同一确认草稿、可空重叠确认凭据"，没有明确区分"有计划确认"和"无计划补记"两种路径。plannedSnapshot 字段在无计划时应为空。
- **验证方式**：静态推演可确认合同允许，但需 1C 明确 ConfirmActual 的两种输入模式。
- **严重程度**：中
- **修订建议**：在 1C 中明确 ConfirmActual 的两种模式：(1) 有活动计划时，封存计划并保存 plannedSnapshot；(2) 无计划（从手牌补记）时，plannedSnapshot 为空，实例直接退出手牌。两种模式共用 factId 唯一性约束。

#### R-A03｜确认完成后，定义被修改，历史事实的快照是否更新

- **场景**：用户用定义 D（标题"晨跑"，25 分钟）创建实例 X，打出并确认完成（Fact 包含行为快照"晨跑/25分钟"）。然后用户修改定义 D 的标题为"晨间跑步"，时长改为 30 分钟。
- **合同规则**：第 3 节"定义快照保证'原卡改名'不会改写手牌含义或历史事实"；第 4 节约束 1"定义改动不覆盖实例与事实快照"。
- **预期**：Fact 的行为快照仍为"晨跑/25分钟"，不变。实例 X 的定义快照也不变。新定义只影响以后接受的新实例。
- **问题**：合同明确了快照不变。但 UI 显示 Fact 时，是显示快照中的标题"晨跑"，还是显示当前定义标题"晨间跑步"？如果显示当前定义标题，用户会误以为事实被修改了。如果显示快照标题，用户可能困惑"为什么和定义不一样"。
- **验证方式**：静态推演。
- **严重程度**：中
- **修订建议**：在 1C 中明确：事实展示使用行为快照中的标题和时长；如与当前定义不同，可显示"原定义已修改"提示，但不替换快照内容。

### B. 并发完成

#### R-B01｜两窗口不同 commandId 同时确认同一实例，IndexedDB 事务隔离级别

- **场景**：窗口 A 提交 ConfirmActual（commandId=A1，instanceId=X，实际区间 09:00-09:30）。窗口 B 同时提交 ConfirmActual（commandId=B1，instanceId=X，实际区间 09:00-09:30）。两个请求几乎同时到达 IndexedDB。
- **合同规则**：第 6 节"两个不同请求同时确认同一实例，由事务内的唯一事实约束拦截第二个"；约束 3"同一实例最多一个活动计划、最多一个完成事实"。
- **预期**：只有一个成功，另一个返回 ALREADY_CONFIRMED 或 FACT_LOCKED。绝无两个 Fact。
- **问题**：合同依赖"事务内的唯一事实约束"。但 IndexedDB 的事务隔离级别是 read committed（读写事务中的读取可以看到其他已提交事务的写入，但看不到未提交的）。如果两个事务同时开始，都读取到"无 Fact"，都通过校验，都尝试写入 Fact，IndexedDB 是否有唯一索引约束？合同没有指定 Fact 的 instanceId 是否有唯一索引。如果没有唯一索引，两个事务可能都成功写入，产生两个 Fact。
- **验证方式**：需运行时验证（阶段 2 实现后，用两窗口同时提交测试）。
- **严重程度**：阻断
- **修订建议**：在 1C/1F 中明确：Fact 集合的 instanceId 必须建立唯一索引（或在事务内先加锁再校验）；store.commit 的事务必须包含"读取当前 Fact → 校验无重复 → 写入 Fact"的原子序列，不能依赖 UI 层按钮禁用。

#### R-B02｜响应丢失后重试，与另一窗口的新请求同时到达

- **场景**：窗口 A 提交 ConfirmActual（commandId=A1），事务成功写入 Fact，但 HTTP/IndexedDB 响应丢失，窗口 A 显示"保存中"。用户在窗口 A 点击重试（同一 commandId=A1）。同时窗口 B 提交 ConfirmActual（commandId=B1，同一 instanceId=X）。
- **合同规则**：第 6 节"相同请求重试复用结果，不重新分配事实 ID/confirmedAt"；"先验证 epoch；然后允许匹配的成功回执重试返回原引用；未见回执才校验 revision 并执行"。
- **预期**：A1 重试返回原 Fact 引用（复用成功回执）。B1 被唯一约束拦截，返回 ALREADY_CONFIRMED。
- **问题**：合同说"先验证 epoch；然后允许匹配的成功回执重试返回原引用"。但 A1 的成功回执保存在哪里？合同说"在 Data 中保存 commandId、命令类型/业务输入指纹和结果引用回执"。如果回执保存在 Data 中，A1 重试时读取 Data 中的回执，匹配 commandId，返回原引用。这是对的。但如果回执保存在本地 Envelope 元数据中（而不是 Data 中），恢复后的 Data 不包含回执（D012 要求 Data 与备份相等），A1 重试时找不到回执，会重新执行？合同说生命周期回执不追加到 Data，但普通业务命令的回执应该在 Data 中。需要明确区分。
- **验证方式**：静态推演。
- **严重程度**：高
- **修订建议**：在 1C 中明确：普通业务命令（ConfirmActual、PlaceAction 等）的成功回执保存在 Data 的业务集合中（如 Fact 自身包含 sourceCommandId，或独立的 commandReceipts 集合），恢复后仍然存在；生命周期命令（RestoreWorkspace、ClearWorkspace）的回执只在 Envelope 元数据中，不进入 Data。

#### R-B03｜两窗口同时对同一 Capture 调用 ResolveCaptureToAction

- **场景**：窗口 A 和窗口 B 同时对同一 captureId=C1 调用 ResolveCaptureToAction（不同 commandId），都想把捕获转成行动实例。
- **合同规则**：第 6 节 ResolveCaptureToAction"已处理时同请求返回原结果，另请求不得再生成"。
- **预期**：只有一个成功，产生一个实例，Capture 标记 resolved。另一个返回错误（Capture 已处理）。
- **问题**：与 R-B01 相同的事务隔离问题。Capture 的 status 字段从 unprocessed 变为 resolved，如果两个事务同时读取到 unprocessed，都通过校验，可能产生两个实例。需要 Capture 的 id 唯一索引或事务内写锁。
- **验证方式**：需运行时验证。
- **严重程度**：高
- **修订建议**：同 R-B01，在 store.commit 事务中保证"读取 Capture 状态 → 校验未处理 → 修改状态 + 创建实例"的原子性；Capture.id 作为唯一键。

### C. 错录

#### R-C01｜确认时填错实际区间，确认后无法纠正区间本身

- **场景**：用户实际 09:00-10:00 完成了任务，但确认时误填为 09:00-11:00。确认后发现错误。
- **合同规则**：D008"确认后原事实的内容与实际时间在应用内永久不可修改"；第 4 节"已有 Fact | 追加说明 | 新 Annotation；Fact 与已有 Annotation 字段完全不变"。
- **预期**：用户只能追加说明"实际是 09:00-10:00，填错了"。Fact 的实际区间永远显示 09:00-11:00。
- **问题**：这是 D008 的直接后果，用户已决定。但需要确认用户是否理解"错录"和"反悔"的区别。错录是操作失误（手抖填错），反悔是正常完成后想改变记录。D008 不区分这两种情况，都不允许修改。合同没有提供"纠错"的特殊路径（比如"确认后 5 分钟内可修改"）。如果用户需要纠错能力，必须在 1C 明确提出，否则按 D008 执行。
- **验证方式**：静态推演。这是产品决策问题，不是合同漏洞。
- **严重程度**：中（需用户确认是否接受）
- **修订建议**：在 1C 中向用户确认：错录（操作失误）是否也适用永久锁定？如果需要有限纠错窗口（如确认后 2 分钟内可修改实际区间），必须作为 D008 的例外明确写入合同；否则按永久锁定执行，UI 在确认前增加"请核对实际区间"的二次确认提示。

#### R-C02｜确认时选错实例，错误事实无法删除

- **场景**：用户手牌中有实例 A（"写报告"）和实例 B（"打电话"）。用户想确认 A 完成，但误点了 B 的确认按钮。确认 B 完成后发现选错了。
- **合同规则**：D008"不能撤回成未完成"；第 4 节"已有 Fact | 再次完成、移动、回收、改名/时间 | 拒绝"。
- **预期**：B 的 Fact 永久存在。A 仍然未完成。用户只能给 B 追加说明"误操作，实际未完成"。
- **问题**：与 R-C01 类似，但更严重——选错实例意味着产生了一个完全虚假的事实。D008 不允许删除。用户是否需要"删除错误事实"的能力？合同没有提供。如果用户不能接受，必须在 1C 提出替代方案（如"确认前预览实例名称和实际区间，二次确认"）。
- **验证方式**：静态推演。
- **严重程度**：高（需用户确认是否接受）
- **修订建议**：在 1C 中向用户确认：误确认（选错实例）是否也适用永久锁定？建议至少在确认 UI 中显示实例名称、实际区间、完成标准的预览，要求用户点击"确认完成"（不是一键完成），减少误操作概率。如果用户需要"删除误确认"能力，必须作为 D008 的例外明确写入。

#### R-C03｜确认结束时间填成未来时间

- **场景**：现在是 10:00。用户确认实例 X 完成，实际开始 09:00，实际结束误填为 11:00（未来时间）。
- **合同规则**：P03"实际按分钟且结束不晚于确认"，但标注为"建议待 1C"，不是已定规则。
- **预期**：未定。如果允许未来结束时间，Fact 的实际区间包含未来时间，这在逻辑上不合理（还没到 11:00 怎么已经结束了？）。如果拒绝，需要明确错误码和提示。
- **问题**：P03 是草案推荐，未冻结。1A 没有明确"确认结束时间不得在确认时刻之后"是强制规则还是建议。如果不强制，用户可能误填未来时间，产生逻辑矛盾的事实。
- **验证方式**：静态推演。
- **严重程度**：高
- **修订建议**：在 1C 中明确：ConfirmActual 必须校验实际结束时间 <= 确认时刻（confirmedAt），否则返回 INVALID_ACTUAL_TIME。确认时刻使用服务器/本地时钟，用户可修改本地时钟但应用不承诺可信时间戳（合同已说明）。如果用户需要预填未来计划时间，那是 PlanPlacement 的功能，不是 ConfirmActual。

### D. 旧备份恢复

#### R-D01｜恢复后旧窗口的未保存草稿如何处理

- **场景**：用户在窗口 A 编辑 Schedule 当天安排（草稿模式，未保存）。然后在窗口 B 执行完整备份恢复（替换整个 Data）。
- **合同规则**：第 6 节"旧窗口尚未发送或排队的动作返回 WORKSPACE_REPLACED"；第 7 节"恢复后的 Data 按 JSON 结构逐字段相等"。
- **预期**：窗口 A 收到 WORKSPACE_REPLACED，页面显示"工作区已被替换，请重新载入"。草稿保留在窗口 A 的内存中。
- **问题**：草稿保留在内存中，但用户重新载入后草稿丢失（因为重新载入从 Data 读取，Data 中没有草稿）。用户在恢复前编辑的草稿是否应该在恢复后保留？合同说普通保存失败时"用户草稿保留"，但恢复是生命周期操作，不是普通保存失败。如果草稿保留，用户可能在恢复后的新数据上继续编辑旧草稿，导致混乱。如果草稿不保留，用户可能丢失未保存的工作。
- **验证方式**：静态推演。
- **严重程度**：高
- **修订建议**：在 1C 中明确：恢复/清空操作前，UI 应检查当前窗口是否有未保存草稿，提示"恢复将丢弃未保存的修改，是否继续？"。恢复后旧窗口的草稿应被清除（不保留），因为草稿是基于旧 Data 的，在新 Data 上无效。用户如需保留草稿内容，应在恢复前手动复制。

#### R-D02｜恢复操作是否生成 History 事件

- **场景**：用户执行完整备份恢复。恢复后 Data 等于备份。
- **合同规则**：D012"不把当前工作区中、备份生成后新增的计划、事实、批注或其它数据自动合并进来"；第 7 节"不在 Data 中追加'已恢复'事件"。
- **预期**：恢复后的 Data 中没有"已恢复"的 History 事件。Data 与备份逐字段相等。
- **问题**：现有代码的 store.commit 会在每次提交时记录 History。如果恢复操作走普通 commit 路径，会生成 History 事件，破坏 D012 的相等性。合同说恢复操作"在一个事务里替换 Data、更新本地提交令牌和必要恢复元数据"，没有说走普通 commit。但需要明确恢复路径不经过 planner.record()，否则会产生 History。
- **验证方式**：需运行时验证（阶段 2 实现恢复后，检查恢复后的 Data.history 是否与备份一致）。
- **严重程度**：阻断
- **修订建议**：在 1C/1F 中明确：RestoreWorkspace 和 ClearWorkspace 使用独立的存储事务，不调用 planner.record() 或任何领域命令的 History 记录逻辑；直接替换 Data 并更新 Envelope 元数据。恢复后的 Data.history 必须与备份完全一致（数组顺序、事件内容都不变）。

#### R-D03｜恢复旧版本备份时，"只读适配层"的定义不明确

- **场景**：用户导入一个 schemaVersion=2 的旧备份（不是当前版本 3）。
- **合同规则**：第 7 节"受支持旧版本先按原版本精确保存，以只读适配层查看；用户另行选择'升级数据'时才进入可预览迁移"。
- **预期**：旧备份可以查看，但不能修改。用户选择升级后才迁移到新版本。
- **问题**："只读适配层"没有定义。是一个独立的 UI 模式（所有写按钮禁用）？还是说旧数据存储在单独的 IndexedDB 存储中，应用以只读模式打开？用户在只读适配层中能否导出数据？能否查看事实和计划？合同没有明确。
- **验证方式**：静态推演。
- **严重程度**：中
- **修订建议**：在 1C 中明确：只读适配层的实现方式——建议将旧版本 Data 存储在独立的 Envelope 中（标记为 readOnly=true），UI 加载时检测到 readOnly 后禁用所有写操作入口，只允许查看和导出。升级操作将旧 Envelope 迁移为新 Envelope，并删除旧 Envelope（或保留为归档）。

### E. 清空

#### R-E01｜清空前下载备份与确认之间，另一窗口修改数据

- **场景**：用户点击"清空工作台"，应用自动下载当前完整备份。然后用户在确认对话框中停留了 30 秒（阅读确认文字）。在这 30 秒内，窗口 B 修改了数据（新增一个捕获）。用户点击"确认清空"。
- **合同规则**：D013"清空操作完成后，当前工作区为全新空状态"；第 7 节"清空前下载的完整备份是用户自行找回旧状态的来源"。
- **预期**：清空的是最新数据（包含窗口 B 新增的捕获）。但下载的备份是 30 秒前的旧数据（不包含窗口 B 的修改）。用户恢复备份后，窗口 B 的修改丢失。
- **问题**：清空前下载的备份与实际清空的数据不一致。合同没有要求在确认清空时重新下载备份，也没有要求锁定工作区防止在确认期间修改。如果用户在确认期间有其他窗口修改数据，清空前的备份就不完整。
- **验证方式**：静态推演。
- **严重程度**：高
- **修订建议**：在 1C 中明确：清空确认对话框打开时，应记录当前 revision。用户点击确认时，重新核对 revision 是否变化。如果变化（另一窗口在确认期间修改了数据），提示"数据已变化，是否重新下载备份后再清空？"，并提供"重新下载并清空"和"取消"两个选项。不允许在备份过期的情况下直接清空。

#### R-E02｜清空后刷新页面，bootstrap 是否自动生成 Day

- **场景**：用户清空工作台。然后刷新页面。
- **合同规则**：D013"清空后工作区彻底空白"；第 7 节"不生成空 Day/Bootstrap 历史"；第 7 节"推荐将当前启动 Bootstrap 改成只读今日投影加显式 PrepareDay"。
- **预期**：刷新后页面空白，无 Day、无例行实例、无 History。Today 页面显示空态，提示"准备今天"或类似显式操作入口。
- **问题**：现有代码的 bootstrap 在页面加载时自动运行，会生成当天 Day 和例行实例。合同说要改成"只读今日投影加显式 PrepareDay"，但这是推荐方案，未冻结。如果不修改 bootstrap，清空后刷新会立即生成 Day 和 History，违反 D013。
- **验证方式**：需运行时验证（阶段 2 实现清空后，刷新页面检查 Data）。
- **严重程度**：阻断
- **修订建议**：在 1C 中明确：清空后的初始化必须不触发任何数据写入。bootstrap 必须拆分为"只读投影计算"（不写 Data）和"显式 PrepareDay"（用户主动调用时才写 Day/例行实例/History）。清空后刷新只运行只读投影，不写 Data。Today 空态提供"准备今天"按钮，用户点击后才调用 PrepareDay。

#### R-E03｜清空失败时，恢复点是否保留

- **场景**：用户执行清空。IndexedDB 事务在删除恢复点时失败（磁盘满或浏览器配额限制）。
- **合同规则**：第 7 节"恢复/清空失败时不能只更新 epoch、清掉恢复点或写入半份 Data"。
- **预期**：事务整体回滚，Data、恢复点、epoch/revision 都保持清空前状态。用户看到"清空失败，数据未改变"的提示。
- **问题**：合同明确了失败时整体回滚。但需要确认实际实现中，清空操作是在一个 IndexedDB 事务中完成所有删除（Data + previous + pre-p1a + 其他恢复点），还是分多个事务。如果分多个事务，第一个事务成功（删除 Data），第二个事务失败（删除恢复点失败），就会出现"Data 已空但恢复点还在"的半清空状态。
- **验证方式**：需运行时验证（模拟事务失败）。
- **严重程度**：高
- **修订建议**：在 1F 中明确：ClearWorkspace 必须在单个 IndexedDB 读写事务中完成所有操作（删除 Data、删除所有恢复点、更新 epoch/revision）。事务失败时整体回滚，不允许部分提交。store 层需提供原子清空 API。

### F. 跨午夜

#### R-F01｜跨午夜计划的目标日期归属

- **场景**：用户在 2026-09-24 23:50 打出一张 25 分钟卡，计划区间 23:50—次日 00:15。
- **合同规则**：第 5.2 节"实际归属日期建议按实际开始在记录时区的日期；日视图可显示任何与该日相交的片段"；第 3 节 PlanPlacement 有"可选目标日期"。
- **预期**：计划的目标日期是 2026-09-24（开始日期）。日视图在 09-24 显示 23:50-00:00 片段，在 09-25 显示 00:00-00:15 片段。
- **问题**：合同说"目标日期"是可选字段。但打出操作时，用户选择的是开始时间（23:50），目标日期是否自动设为开始日期？如果用户在 09-25 的视图中打出 00:15 结束的卡，目标日期是 09-25 还是 09-24？合同没有明确打出时目标日期的计算规则。
- **验证方式**：静态推演。
- **严重程度**：中
- **修订建议**：在 1C 中明确：PlaceAction 的目标日期 = 计划开始时间在记录时区的日期。用户在日视图中操作时，日视图日期只影响默认显示范围，不改变目标日期的计算。跨午夜计划在两日视图中都显示片段，但手牌/计划列表中只归属开始日期。

#### R-F02｜跨午夜事实的完成次数统计

- **场景**：实例 X 的实际区间 23:50—次日 00:15，已确认完成。
- **合同规则**：第 5.2 节"完成次数只按唯一 factId 及开始日期计一次"；"按日统计分别计交集时长"。
- **预期**：完成次数在开始日期（前一天）计 1 次。时长统计在前一天计 10 分钟，次日计 15 分钟。
- **问题**：合同明确了统计规则。但 UI 显示时，用户在次日视图看到这个事实的片段（15 分钟），可能误以为是次日完成的。日视图是否需要标注"跨日事件，开始于昨日"？合同没有明确显示规则。
- **验证方式**：静态推演。
- **严重程度**：低
- **修订建议**：在 1C/3A 中明确：跨午夜事实在非开始日期的日视图中显示时，标注"开始于昨日"或使用视觉区分（如虚线边框），避免用户误认为是当日完成。

#### R-F03｜夏令时跨午夜计划的时长计算

- **场景**：America/New_York 时区，2026-11-01（秋 back 日，01:00-02:00 重复一次）。用户打出计划 23:00—次日 01:30。
- **合同规则**：第 5.2 节"不能用固定的 24 小时毫秒数计算下一当地零点"；"重复的本地时间返回两个带偏移的选择"。
- **预期**：23:00—次日 01:30 的实际时长是 2.5 小时（因为 01:00-02:00 重复了一次，从 23:00 到 01:30 经过了 2.5 小时？不对，让我算一下：23:00 到 01:00 是 2 小时，然后 01:00 重复一次（回到 01:00），再到 01:30 是 0.5 小时，总共 2.5 小时？不对，秋 back 日是凌晨 2 点变回 1 点，所以 01:00-02:00 这一小时出现两次。从 23:00 到次日 01:30：23:00→00:00（1h）→01:00（1h）→01:00（重复，0h）→01:30（0.5h）= 2.5h。对的。
- **问题**：合同说不能用固定 24 小时毫秒数计算。但计划时长是由卡牌预设时长决定的（比如 150 分钟 = 2.5 小时），不是由开始/结束时间差计算的。如果用户打出一张 150 分钟卡到 23:00，结束时间应该是 23:00 + 150 分钟 = 01:30（考虑夏令时）。时间服务必须正确处理夏令时的时间点加法。合同说"时间服务的依赖库选择留到 1F"，但接口必须能给出正确结果。
- **验证方式**：需运行时验证（阶段 2 实现时间服务后，用夏令时日期测试）。
- **严重程度**：高
- **修订建议**：在 1F 中明确：时间点加法（startAt + duration）必须使用时区感知的时间库，不能用简单的毫秒加法。C13 已覆盖夏令时的不存在/重复时间，但还需要覆盖"时间点加法"的正确性。在 1C 中补充验收用例：夏令时跨午夜计划的结束时间计算。

### G. 固定块误拖

#### R-G01｜解锁固定块后拖动到与其他固定块冲突的位置

- **场景**：用户解锁固定块 A（09:00-10:00）。拖动 A 到 09:30-10:30，与固定块 B（10:00-11:00）重叠 30 分钟。释放。
- **合同规则**：第 4 节约束 6"解锁不允许覆盖其他记录"；第 5.3 节"取它们的区间并集，再从查询范围中相减"。
- **预期**：移动被拒绝，返回 SLOT_OCCUPIED 或类似错误。固定块 A 保持原位。
- **问题**：合同明确了解锁不允许覆盖其他记录。但"解锁"的语义是"允许移动这个固定块"，还是"允许这个固定块被其他操作覆盖"？合同说"解锁仅授权明确对象/版本的本次修改"，所以解锁 A 只允许修改 A，不允许 A 覆盖 B。这是对的。但 UI 上是否需要在拖动预览时就显示"与固定块 B 冲突"的红色提示？合同没有明确预览反馈。
- **验证方式**：静态推演。
- **严重程度**：低
- **修订建议**：在 1C/3A 中明确：拖动固定块时，预览区间与其他固定块/计划/事实重叠时，显示红色冲突提示；释放时拒绝移动。解锁只移除该固定块自身的"不可拖动"限制，不改变冲突检测规则。

#### R-G02｜模板应用到某天时，与当天已有固定块重叠

- **场景**：某天已有固定块 A（09:00-10:00，当天例外）。用户将模板 T（含固定块 09:30-10:30）应用到该天。
- **合同规则**：第 4 节约束 6"模板应用只更新允许改动的日程对象，不能替换整天时顺带清除活动卡牌或事实"。
- **预期**：模板应用时，模板中的固定块与当天已有固定块 A 重叠。应该拒绝、合并、还是覆盖？
- **问题**：合同没有明确模板应用时的冲突处理规则。"只更新允许改动的日程对象"——哪些是"允许改动的"？当天已有的固定块 A 是用户手动创建的例外，是否允许被模板覆盖？如果不允许，模板应用应该失败还是跳过冲突块？合同没有明确。
- **验证方式**：静态推演。
- **严重程度**：高
- **修订建议**：在 1C 中明确：ApplyDayTemplate 的冲突处理规则——模板中的块与当天已有块（固定/灵活/事实）重叠时，列出冲突并要求用户选择：(1) 跳过冲突块，只应用不冲突的块；(2) 取消整个模板应用。不允许静默覆盖当天已有的块。模板应用只新增/更新模板来源的块，不删除用户手动创建的例外块。

#### R-G03｜解锁状态的超时与刷新

- **场景**：用户解锁固定块 A。然后离开电脑 1 小时。回来后拖动 A。
- **合同规则**：第 4 节约束 6"解锁仅授权明确对象/版本的本次修改"。
- **预期**：解锁是一次性的，只授权"本次修改"。如果用户解锁后没有立即修改，解锁状态应该在什么条件下失效？
- **问题**：合同没有明确解锁状态的生命周期。是一次性（修改一次后失效）？还是有超时（如 5 分钟）？还是刷新页面后失效？如果解锁状态永久有效，用户解锁后忘记了，后续误操作可能移动固定块。如果解锁状态只在当前 UI 会话中有效，刷新后需要重新解锁，这更安全。
- **验证方式**：静态推演。
- **严重程度**：中
- **修订建议**：在 1C 中明确：固定块解锁是 UI 层的临时状态，不保存在 Data 中。刷新页面或切换页面后解锁状态失效，需重新解锁。解锁后只允许一次修改操作（移动或取消），操作完成后自动重新锁定。不设置超时，但 UI 应显示"已解锁，可移动"的明显提示。

### H. 取消后重复打出

#### R-H01｜撤回计划后，实例回手牌，然后修改实例时长再打出

- **场景**：实例 X（预设 15 分钟）打出到 09:00-09:15（Plan A）。撤回 Plan A，X 回手牌。用户修改 X 的预设时长为 30 分钟。然后打出 X 到 10:00-10:30（Plan B）。
- **合同规则**：第 6 节 UpdateOpenInstance"有活动计划时改时长须原子校验新区间"；第 4 节"活动计划 | 撤回 | Plan 标记 retracted，原实例回手牌"。
- **预期**：撤回后 X 没有活动计划，可以修改时长。修改后打出产生 Plan B（30 分钟）。Plan A 保持 retracted，历史记录中是 15 分钟。
- **问题**：合同允许这个操作。但 Plan A 的历史记录中，计划的时长是 15 分钟（基于当时的实例预设）。Plan B 是 30 分钟。同一实例的两次计划时长不同，这在统计时可能造成困惑。合同说"定义快照保证原卡改名不会改写历史事实"，但实例的预设时长修改是否也需要快照？实例的定义快照在创建时保存，修改实例时长是否更新快照？如果更新，Plan A 的历史引用的是旧快照还是新快照？
- **验证方式**：静态推演。
- **严重程度**：中
- **修订建议**：在 1C 中明确：实例的定义快照在创建时保存，修改实例时长（UpdateOpenInstance）时更新实例的当前快照，但不修改已有 Plan/Fact 中的快照引用。Plan A 的历史记录引用 Plan A 创建时的实例快照（15 分钟），Plan B 引用 Plan B 创建时的快照（30 分钟）。统计时按各 Plan/Fact 自身的快照计算。

#### R-H02｜撤回计划后，"撤销撤回"导致同一实例两个活动计划

- **场景**：实例 X 打出到 09:00-09:15（Plan A）。用户撤回 Plan A（X 回手牌，Plan A 标记 retracted）。然后用户点击"撤销撤回"（如果 UI 提供此功能），Plan A 恢复为 active。同时用户已经打出 X 到 10:00-10:15（Plan B）。
- **合同规则**：第 4 节约束 3"同一实例最多一个活动计划"；第 6 节 RetractPlan"封存撤回并回手牌"。
- **预期**：如果"撤销撤回"允许，Plan A 恢复 active 时，X 已有活动计划 B，应该返回错误或要求先撤回 B。不允许同一实例两个活动计划。
- **问题**：合同没有明确是否提供"撤销撤回"功能。RetractPlan 的结果是"Plan 标记 retracted，原实例回手牌"。如果用户想恢复撤回的计划，是重新打出（产生新 planId），还是有"撤销撤回"命令（恢复原 planId）？合同说"重新打出产生新 planId"，暗示没有"撤销撤回"命令。但如果 UI 提供了"撤销"按钮（常见的 UX 模式），就需要明确这个命令的语义。
- **验证方式**：静态推演。
- **严重程度**：中
- **修订建议**：在 1C 中明确：不提供"撤销撤回"命令。撤回的计划保持 retracted，用户如需重新安排，从手牌重新打出（产生新 planId）。如果 UX 需要"撤销"按钮，该按钮只在撤回操作后的短时间内（如 5 秒）可用，且本质是重新打出（新 planId），不是恢复原 planId。

#### R-H03｜撤回操作失败但 UI 显示已撤回，用户重新打出导致冲突

- **场景**：用户点击撤回 Plan A。存储操作失败（STORAGE_FAILED），但 UI 乐观更新显示已撤回（X 回手牌，Plan A 消失）。用户打出 X 到新区间，产生 Plan B。
- **合同规则**：第 6 节"STORAGE_FAILED 保留草稿和原数据，允许同一请求重试"；约束 3"同一实例最多一个活动计划"。
- **预期**：撤回失败时，Plan A 仍然 active，X 不在手牌中。UI 不应显示已撤回。用户打出 X 应该返回"已安排"错误。
- **问题**：合同说 STORAGE_FAILED 保留原数据，但 UI 是否使用乐观更新？如果 UI 在点击撤回时立即更新显示（不等待存储结果），存储失败后需要回滚 UI 状态。如果回滚失败或不及时，用户看到的状态与实际 Data 不一致，可能导致误操作。合同没有明确 UI 是否使用乐观更新，以及失败时的回滚机制。
- **验证方式**：需运行时验证（阶段 2 实现后，模拟存储失败）。
- **严重程度**：高
- **修订建议**：在 1C 中明确：所有写操作（撤回、打出、确认等）不使用乐观更新。UI 在操作期间显示"保存中"状态（按钮禁用、loading 指示器），等待存储结果返回后再更新显示。失败时显示错误提示，UI 状态保持操作前不变。这避免了乐观更新与实际数据不一致的问题。

## 三、C01—C19 验收种子审查补充

1A 草案第 9 节已列出 C01—C19。以下是对这些用例的补充审查和遗漏：

| 1A 用例 | 审查结论 | 补充 |
|---|---|---|
| C01 | 成立。查看不写 Data 需 UI 验证。 | 补充：连续点击"查看"10 次，Data 不变。 |
| C02 | 成立。不拼接空隙是核心规则。 | 补充：空隙 09:00-09:20（20分钟）+ 09:20-09:25（5分钟，被其他计划占用后释放）= 25 分钟，但中间曾经被占用，是否允许？应按提交时的最新状态判断，不允许拼接历史空隙。 |
| C03 | 成立。双十二小时双落点。 | 补充：如果用户选择上午落点后，另一窗口占用了下午落点，下午轮廓应消失。 |
