# CardGrid 项目定位与 README 规范

版本：v0.1  
用途：指导 GitHub 项目主页重构，并作为产品方向的长期依据。

## 第一部分：CardGrid 项目定位

### 项目是什么？

CardGrid（卡格工作台）是一款面向个人用户的本地优先个人工作流系统。它从每日概览出发，帮助用户审阅安排、根据计划行动，并通过持续记录形成长期积累。当前版本围绕 Today、Inbox、Schedule 和本地数据管理展开。

### 为什么做？

个人的日程、待办、临时想法和项目计划常分散在不同工具中。每天开始行动时，用户仍要自己整合这些信息：今天该做什么、安排是否合理、哪些事情值得推进。CardGrid 希望提供一个以个人为中心的工作空间，让用户从计划进入执行，并通过执行获得长期反馈。

### 解决什么问题？

1. **缺少每日行动中心**：Today 汇总当天安排、重点和例行事项，帮助用户理解今天并开始行动。
2. **计划与现实脱节**：区分原始安排、当天调整和实际完成；临时变化不应抹去计划历史，也不应擅自改写长期模板。
3. **临时信息难以进入工作流**：先把想法收进 Inbox，再决定归档、丢弃或转为可执行的 Card，不要求捕获时就填完整任务信息。
4. **缺少长期积累反馈**：一天不是孤立的。持续记录应帮助用户看见完成了什么、推进了什么，以及计划与现实的差异。长期目标与项目关联属于后续发展方向，不作为当前已完成功能宣传。

### 目标用户是谁？

核心用户是希望自己管理时间、任务和个人工作流的个人用户，包括学生、创作者、独立开发者和知识工作者。当前不以企业团队协作、组织管理或多人项目协同为主要方向。

### 核心设计理念

- **Today 优先**：打开软件先回答“今天是什么样的”，再决定“现在做什么”。
- **用户自主配置**：从空白工作区开始，建立自己的日型、星期安排和工作方式，而非接受预置的私人计划。
- **计划与执行结合**：记录计划、调整和完成，帮助用户观察差异。
- **本地优先**：不依赖账号，工作数据默认保存在当前浏览器，备份由用户掌握。
- **围绕个人工作流扩展**：未来可以连接习惯、项目、个人复盘和 AI 辅助规划，但扩展必须服务个人的日常行动。

### 未来希望发展成什么？

CardGrid 希望逐步成为一套可由个人塑造的日常工作系统：从 Today 安排一天，连接阶段性项目和例行习惯，再通过轻量复盘理解长期积累。这个方向需要真实使用与验证；不应把未来探索写成当前已有能力。

## 第二部分：CardGrid README 编写规范

### README 的目标与读者

README 是项目主页，不是开发日志。它需要让陌生人在五分钟内理解并判断是否使用或关注 CardGrid，同时照顾三类读者：普通读者想知道产品是什么、为什么值得尝试；准备使用的人想知道如何安装、运行和保护数据；开发者想知道技术结构、当前状态与参与方式。

### 信息结构

README 按以下顺序组织。功能与路线图必须区分“当前已有”“计划中”“未来探索”。

1. **项目标题**：`CardGrid · 卡格工作台`。
2. **一句话介绍**：先讲产品价值，不在开头解释技术实现或开发过程。
3. **项目介绍（Why）**：说明工具分散带来的问题，以及从计划进入执行的产品方向。
4. **核心特点**：用三到六点概括 Today 优先、可配置、本地优先及计划与执行结合等价值。
5. **当前功能**：以用户视角介绍 Today、Inbox、Schedule 和数据管理，而非按代码目录罗列。
6. **界面预览**：展示与当前版本一致、没有个人数据的截图；有公开 Demo 后再补地址。图片应帮助读者判断是否愿意打开产品。
7. **开始使用**：列出 Node.js 版本、安装与运行命令、访问地址和首次使用路径。
8. **数据与隐私**：解释本地存储、账号要求、备份方式和主要数据风险。
9. **开发说明**：提供技术栈、核心目录或文件、测试与构建方式。
10. **Roadmap**：分别标明已完成、计划中、未来探索，不以未经验证的能力充当现状。
11. **贡献方式**：说明当前可用的 Issue、Pull Request 路径与基本约定；仓库未开放时不暗示任何人都能参与。
12. **License**：明确当前私有、尚未选择开源许可证；公开前再作决定。

### 完成标准

陌生人打开项目主页后，应能回答：这是什么、为什么存在、适合谁、怎么体验、如何运行、当前做到哪里，以及如何参与。README 不记录作者学习过程、每次修改或踩坑；这些内容应进入开发日志、Issue、CHANGELOG 或项目文档。

重构时保留已准确的“开始使用”“数据与隐私”“开发”信息，前置产品定位与功能展示，再补充界面预览和 Roadmap，最后统一语言风格。任何陈述都以当前代码和实际运行结果为准。
